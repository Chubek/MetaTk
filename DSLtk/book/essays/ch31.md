## A visitor is a checked vocabulary of operations

An AST tag is a runtime string. A compiler pass that switches on those strings
can accidentally omit a tag, mistype a spelling, or silently ignore a node
introduced by a later grammar change. DSLtk's visitor machinery makes the
accepted tag vocabulary explicit and checks that the supplied handlers cover
it. The schema can come from a runtime prototype tree or from a compile-time
tree of schema types.

The resulting visitor remains an ordinary object containing concrete handler
types in a tuple and a runtime collection of schema tags. It is not generated
machine code, a JIT compiler, or a new virtual class hierarchy. Template
instantiation connects each case's compile-time tag to its callable, while
runtime node tags determine which case is invoked. This hybrid arrangement
fits an AST whose node vocabulary is known more statically than its values.

The most important limitation should be understood immediately: the schema
checks tag coverage, not complete grammar structure. It does not establish
that `add` has two children, that a number payload is numeric, or that an
assignment's left child is an identifier. Those are semantic and structural
checks that handlers or a separate validation pass must perform.

## Cases and tag-aware invocation

`on<"number">(handler)` creates a `VisitorCase` whose tag is available as a
static string view. The case stores its callable by value. Invocation checks
whether the callable accepts an `ASTTag<Tag>` followed by the node reference.
If so, the tag-aware form is selected. Otherwise the case invokes the callable
with only the node reference. The compile-time tag can help a generic handler
specialize behavior without reparsing a runtime string.

This selection is based on invocability, so handler signatures matter. A
handler that expects a mutable node cannot be used to walk a const tree in
the same way as a handler accepting `const ASTNode&`. A generic callable
that accepts both forms will take the tag-aware path. Clear signatures are
preferable to overly permissive ones when a pass has a precise mutation
policy.

Capturing a reference in a handler also makes the visitor borrow that external
state. A visitor that increments a local counter is valid only while the
counter remains alive. Copying the visitor copies the closure, not the
referenced object. The tuple's value semantics do not automatically make all
captured dependencies owned. This is the same callable-lifetime issue seen
in pipelines and rewrite rules, now applied to a traversal object.

## Runtime schemas discover tags from a prototype

`derive_visitor` receives an `ASTNode` used as a schema prototype. Construction
walks that prototype and collects distinct tags in first-occurrence order.
Each discovered tag must have at least one registered case. A missing handler
causes construction to throw. The prototype's payload values and exact child
counts are not retained as grammar constraints.

For example, a schema tree `add(number)` is enough to declare the tags `add`
and `number`, even though real addition nodes may have two children. This
compactness is convenient, but calling the prototype a schema can suggest a
stronger structural contract than the code implements. The application should
document the vocabulary check separately from any arity check.

When visiting a node, the visitor first rejects a tag outside the collected
schema vocabulary. It then scans registered cases and invokes the first case
whose tag matches. Duplicate handlers do not form a multicast list; later
matching cases are skipped once one has run. If duplicate registrations are
not meaningful for a project, validate or avoid them at the application level.

## Compile-time schemas move one check earlier

`ASTSchema<Tag,Children...>` records a tag and a tuple of child schema types.
The `ast_schema` factory constructs this type-level shape. The typed
`compile_visitor` overload recursively checks that every schema tag has a
handler using a compile-time predicate and `static_assert`. A missing case
then fails compilation instead of throwing during runtime construction.

After that check, the implementation materializes a runtime prototype tree
and creates the same runtime visitor machinery. Static schema checking does
not remove all runtime tag comparisons. It also does not make arbitrary
later AST values structurally conform to the schema. The guarantee is that
the handler set covers the declared vocabulary, not that every input tree is
a well-typed program.

The runtime-schema overload of `compile_visitor` remains useful when the
vocabulary is discovered from external grammars or plugins. Its name should
not be read as a promise of compile-time validation for a runtime argument.
Overload selection determines which check is possible. This is a good example
of why template API documentation should explain both the static and dynamic
paths rather than presenting one broad claim for a shared function name.

## Visit and walk have different scopes

`visit(node)` dispatches exactly one node. `walk(node, order)` performs a
recursive traversal and dispatches each encountered node. Preorder is the
default: visit the current node, then its children. Postorder reverses that
timing: process descendants first, then visit the current node. Both preserve
the vector's left-to-right child order.

Preorder is natural for emitting an opening delimiter, collecting declared
names before descending, or inspecting a parent's context. Postorder is
natural for bottom-up measurements and transformations that depend on child
results. However, the visitor does not automatically maintain a stack of
environments or return a value from each child. Handlers that need such state
must capture it or use a separate recursive evaluator.

The distinction between traversal and evaluation is important. A visitor that
adds every numeric leaf computes a sum of leaf values, not necessarily the
meaning of an expression tree containing subtraction or multiplication.
To evaluate an expression, the pass needs operator-sensitive combination of
child results. A postorder stack can provide that mechanism, but it is
application logic layered on the visitor's dispatch and traversal.

## Mutation changes the traversal being performed

A mutable preorder handler can replace the current node before the walk
descends into children. The traversal then observes the replacement's child
structure. A postorder handler runs after the old descendants have already
been visited. These are different transformation semantics, and the right
choice depends on whether newly created descendants should be traversed in
the same pass.

Mutating a parent's child vector while iterating over it can invalidate
references and iterators. The public mutable `children` accessor makes such
changes possible, but the visitor does not provide a mutation transaction or
stable node handles. Restrict handlers to safe local replacements, collect
planned edits for a later pass, or use the rewrite engine when its copy-based
bottom-up semantics fit the task.

Deep trees also consume recursive call depth in `walk`. Unlike the directed
graph traversals, this visitor does not use an explicit work stack. An
application handling very deep generated ASTs may need an iterative walker
that calls `visit` on each node. Separating the one-node operation from the
recursive operation makes that extension possible without rebuilding the
handler dispatch logic.

## A complete vocabulary-checked measurement pass

```cpp
#include "DSLtk.hpp"
#include <cassert>
int main() {
  auto schema = dsl::ast_schema<"add">(dsl::ast_schema<"number">());
  std::size_t operators = 0, numbers = 0;
  auto visitor = dsl::compile_visitor(schema,
    dsl::on<"add">([&](const dsl::ASTNode& n) {
      if (n.is_leaf() || n.size() != 2)
        throw std::invalid_argument("add requires two operands");
      ++operators;
    }),
    dsl::on<"number">([&](const dsl::ASTNode& n) {
      if (!n.is_leaf()) throw std::invalid_argument("number must be a leaf");
      ++numbers;
    }));
  auto tree = dsl::node<"add">(dsl::leaf<"number">(2), dsl::leaf<"number">(3));
  visitor.walk(tree);
  assert(operators == 1 && numbers == 2);
  bool rejected = false;
  auto unknown = dsl::leaf<"name">("x");
  try { visitor.visit(unknown); }
  catch (const std::invalid_argument&) { rejected = true; }
  assert(rejected);
}
```

The schema establishes tag coverage at compilation. The `add` handler then
checks arity at runtime, demonstrating that these are separate obligations.
The unknown-node test exercises the visitor's closed vocabulary. A test for
a malformed `add` would exercise the application's structural check instead.
Naming the responsible layer makes failures easier to diagnose.

## Cost and extension choices

The current implementation searches schema tags and then scans cases for
each visited node. With a small language vocabulary this is usually simple
and adequate. With hundreds of tags or a very hot pass, a different dispatch
representation may be useful: interned tag IDs, enum-based dispatch, or a
precomputed lookup table. Such changes should be motivated by measurements,
not by assuming all runtime string comparisons are automatically expensive.

The visitor's main benefit is a checked relationship between vocabulary and
operations. When a new tag is added to a static schema, missing handlers are
reported early. When a runtime grammar introduces an unexpected tag, the
visitor rejects it rather than silently ignoring it. This favors explicit
evolution of compiler passes. An application that intentionally wants a generic
fallback should design that fallback policy separately instead of relying on
an accidental omission.

The D port reaches a similar result using CTFE schema values and native
template mechanisms. Its public visitor operations accept mutable node
references, and alias callables provide a path for generic handlers. As with
the rest of the port, compare coverage, mutation timing, and lifetime behavior
before comparing surface syntax. The reference material below supplies both
forms and connects visitor dispatch to equality-triggered processing.
