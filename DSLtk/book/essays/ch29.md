## Equality changes the optimization problem

A directed rewrite chooses a replacement and discards the old shape from
the current tree. That is effective when a reliable normal form is known.
It can be limiting when an expression has several useful equivalent forms
and the best form depends on later transformations. Equality saturation keeps
alternatives together, allowing later rules to match consequences of earlier
equalities without committing immediately to one final syntax tree.

An e-graph is the data structure that supports this arrangement. An e-class
denotes expressions known equal. An e-node records an operator and child
e-class identifiers. A class may contain several e-nodes, each representing
a different way to construct an expression in that class. Children point to
classes rather than to a single selected child expression, which compactly
represents combinations of equivalent alternatives.

DSLtk implements a compact version of this idea in one C++ class and a
corresponding D class. It includes hash-consing, union-find, congruence
rebuilding, pattern matching, bounded saturation, and minimum-node extraction.
It does not include every analysis and scheduling mechanism found in larger
e-graph frameworks. Studying the small implementation is useful precisely
because the essential invariants remain visible.

## Hash-consing and canonical children

Insertion constructs a key from the node's atom or operator role, quotedness,
operator spelling, and canonical child-class identifiers. An identical key
reuses an existing class rather than allocating a duplicate node. The key
encoding includes lengths and separators so different textual components do
not accidentally collapse into the same concatenated spelling. The map's
hash collisions are resolved by normal key equality.

Canonical child identifiers matter because class merging changes which
identifiers denote the same equivalence class. Two nodes that originally had
different child IDs can become congruent after their children are merged.
The node key therefore canonicalizes each child through `find`. A hash table
built before a merge cannot simply be assumed to remain a complete canonical
index afterward. That is the role of rebuilding.

The union-find implementation compresses paths in `find` and keeps the
smaller root identifier when uniting two different roots. This deterministic
choice is simpler than a rank- or size-based heuristic. The visible ID is
still a handle into the graph; clients should call `find` or equality queries
when they need its current representative. An earlier class ID remains usable
after a union, even though it may no longer be a root.

## Congruence is the crucial invariant

Suppose the graph contains `f(a)` and `f(b)`. If the application establishes
that `a` and `b` are equal, congruence requires `f(a)` and `f(b)` to become
equal as well. The application should not need to add a separate rewrite
rule for every enclosing operator. Equality of corresponding children and
identity of the operator imply equality of the parent constructions.

DSLtk's rebuild process snapshots nodes, canonicalizes their keys, and merges
owners of duplicate canonical keys. A merge can create further congruences,
so the process repeats until stable. It then reconstructs class node lists
and removes duplicate canonical alternatives. This is a global rebuilding
strategy whose clarity is attractive in a small toolkit. Its cost can be
substantial on large graphs, so it should not be described as free maintenance.

Queries such as equality checks, matching, counting, and extraction rebuild
when necessary. Calling `find` only follows the current union-find relation;
it does not itself prove that all parent congruences have already been
discovered. An application that performs direct unions and then wants a fully
canonical structural picture should use the provided rebuilding-aware
operations or call rebuild explicitly.

## Matching binds classes, not selected trees

An e-pattern variable binds to an e-class ID. A repeated variable requires
class equality, not identical printed syntax. If `a` and `b` have been merged,
the pattern `(pair ?x ?x)` can match a node originally inserted as
`(pair a b)`. A conventional tree matcher would reject that subject unless its
two children were structurally equal. The e-graph matcher uses the stronger
knowledge already recorded in the equality relation.

Matching a compound pattern explores compatible e-nodes in a class and
combines child substitutions. Several alternatives can produce several
bindings, and combining matches across children can grow the result set.
The match limit bounds returned records; it does not make pattern search
intrinsically cheap. Rules with repeated broad variables or highly populated
classes deserve particular attention when choosing resource limits.

The binding keys include the question-prefixed variable spelling used by the
S-expression rule language. This differs from first-order `TermSubstitution`,
whose keys are bare variable names. The two maps serve different engines and
should not be exchanged merely because both are called substitutions.
Conversions between term and e-graph representations need explicit naming
and semantic conventions.

## Applying a rule records equality

For every match, the engine instantiates the right side under the binding,
inserts any needed e-nodes, and unites the result with the matched root class.
The left-side representation remains in the graph. The inserted right-side
representation can enable another rule during the same iteration or a later
iteration. Search is oriented by the rule's left side, while the stored
equivalence relation is symmetric.

This distinction explains why a reverse rule can still be useful. Knowing
that two classes are equal does not mean the engine synthesizes every possible
syntax shape in both directions. A reverse-oriented rule supplies another
search-and-construction pattern. Adding both directions indiscriminately can
also generate far more alternatives than the application needs. Rule design
is therefore partly a search-space design problem even though equality itself
is symmetric.

The engine validates each rule's shape and variable discipline before running
it, including hand-constructed rules. It cannot validate the domain law.
A rule that equates division by zero with zero is still an invalid arithmetic
law even if all variables are bound correctly. Trust in the rewrite set is an
application-level premise, and semantic tests should make that premise visible.

## Fixed points and three different budgets

The saturation driver compares a revision counter before and after an
iteration. When no graph revision occurs, the run reports saturation.
Rule applications can still have been observed during that iteration: applying
a rule whose equality is already established need not change the graph.
Application count and graph-change count are therefore different measurements.
An observer callback is not proof that a new equivalence was discovered.

The limits bound iterations, retained nodes during insertion, and total
applications. A run that stops at a limit has a valid partial result, but it
has not established the same fixed-point claim as a saturated run. The report
must be carried alongside the extracted expression when the distinction
matters. Hiding it behind a function that returns only a simplified tree
loses important operational information.

The node budget is temporary during saturation and restored afterward.
An interrupted right-side insertion may have created some subterms before
the budget was reached. Those subterms can remain in the graph without the
unfinished parent having been merged. Resource limits do not promise rollback
to the exact graph state at the beginning of the attempted application. A
caller that needs transactional optimization should work on a disposable
graph instance and publish only the result it accepts.

## Extraction solves a different problem

After saturation, the graph knows many alternatives but has not selected one
for output. DSLtk's extractor minimizes tree node count. It repeatedly computes
candidate costs as one plus the costs of the children and records the cheapest
available node for each class. Infinite cost marks alternatives that cannot yet
be constructed from finite children. Costs only improve until no update occurs.

Cycles do not automatically make extraction impossible. A class may contain
both `a` and `wrap(a)` after a union. The atom is a finite representative, and
the wrapping alternative is more expensive. Choosing the atom breaks the
cycle in the extracted tree. If no finite representative can be found, the
extractor throws rather than recursing forever through an unproductive cycle.

Minimum node count is a structural objective, not a machine-performance model.
It does not account for instruction latency, vectorization, register pressure,
memory traffic, or common-subexpression sharing in the eventual program.
The current API does not accept a custom cost function. Applications should
describe the result as minimum-node extraction within the represented
alternatives, not as globally optimal code generation.

## Observation, mutation, and evidence

`when_equal` checks equality immediately and invokes a callback if the classes
are equal. It is not a subscription that remains registered for future
unions. A caller that wants notifications during a run can use the saturation
observer, but should keep observer accounting separate from the engine's
revision-based convergence criterion. Repeated observations are normal.

The saturation case study demonstrates this concretely. Two identity rules
simplify `(mul (add a 0) 1)` to `a`. The run takes a changing pass and then
a pass that establishes no further revision. Its application count can exceed
the two distinct useful equalities. The case study checks equivalence,
extraction, callback accounting, and semantic evaluation over a finite input
range. These checks are complementary: none alone establishes all of the
others.

An independent interpreter is particularly valuable. It makes explicit the
domain in which the rules are intended to hold, and catches errors in the
rule set or conversion conventions. A finite test sweep remains evidence,
not a universal proof, but it is far stronger than verifying only that the
extracted string is shorter. The detailed API reference below supplies the
construction steps needed for such a workflow.
