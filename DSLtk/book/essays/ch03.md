## A map of the two implementation files

The physical shape of DSLtk is unusually useful for study. The C++ library is
a single header with a long embedded enum-reflection implementation followed
by the toolkit's own namespace. The D library is a single module whose
declarations use native templates, strings, reflection, and compile-time
function evaluation. Understanding the organization means a reader can move
from a line of application code directly to the mechanism that implements it.
There is no generated parser hidden behind a build step and no separately
linked runtime that must be reverse-engineered to understand a basic call.

The C++ namespace `dsl` begins at line 5818 of this snapshot. Its initial
declarations re-export the embedded `magic_enum` public surface. The small
`FixedString` type follows, then feature declarations, the `DSL` base template,
predicate and pipeline wrappers, dispatch, trees, rewrite passes, expression
templates, literals, and functional utilities. Parsing, PEG-style tokenization,
symbolic facilities, byte protocols, visitors, CFG parsing, preprocessing,
graphs, and terms occupy the later regions. Those line numbers are landmarks
for this snapshot rather than permanent API identifiers. Search by symbol when
reading a later revision.

The D module organizes some of the newer graph facilities earlier than the
C++ header does. That rearrangement has no semantic significance. The module
imports selected Phobos names and then declares feature tags, composition,
concrete callable types, and the public facilities. Embedded unit tests live
near the end. A chapter about a feature therefore follows its public purpose,
not necessarily the exact order of declarations in both languages.

## Two layers that must not be confused

The first layer is feature composition. A C++ host inherits
`dsl::DSL<Host, Features...>`. That base expands one nested mixin template per
feature and supplies protected downcast helpers. Some mixins contribute useful
member functions. Others are intentionally empty. An empty mixin gives generic
code something to recognize with `HasFeature`; it does not turn free-standing
library functions into host members.

The second layer is the library of ordinary values and algorithms. A program
can construct `ASTNode`, run `StaticRegex`, build an `EGraph`, or use
`DirectedGraph` without inheriting any DSL base. This independence is not an
accidental escape hatch. It allows a language implementation to adopt only the
representations and algorithms it needs. Feature tags describe a composed
interface; namespace-level facilities provide the implementation vocabulary.

For example, `AST::Mixin` supplies `make_leaf` and `make_node`, but these simply
delegate to the free factories. `Pipeline::Mixin` supplies `wrap`; the actual
pipe operator is found through the right operand's `PipeStage` type. Selecting
`EnumReflection` adds an empty base while the reflection functions remain
namespace re-exports. Understanding this separation avoids both unnecessary
inheritance and mistaken expectations about which members appear on a host.

There are twenty-six built-in tags in the supplied implementations. Counting
tags is useful for navigation, but it is a poor measure of runtime complexity.
An empty marker is tiny while its associated algorithm may be substantial.
Conversely, expression-template operators contribute declarations that the
compiler can optimize away for a particular scalar expression. The cost of a
feature depends on the concrete operations that are instantiated and executed.

## The representation layer

Several representations coexist because they answer different questions.
`ASTNode` is a runtime-tagged tree with textual leaf values. It is convenient
for syntax, diagnostic dumps, and value-based rewrites. `SExpr` preserves atom
versus list structure and quotedness; it is the interchange language for rules
and grammars. `Term` adds first-order variables and ordered function arguments,
so matching and unification have a precise structural interpretation.

An e-graph answers a different question: which expressions are known equal?
Its class identifiers denote equivalence classes, each of which can retain
several e-node alternatives. A term graph instead represents sharing among
concrete term nodes. Two incoming edges can refer to the same reducible
subexpression. Sharing a node and knowing two alternatives equal are related
ideas, but they are not interchangeable representations. Neither should be
described as merely a faster AST without explaining the additional semantics.

This distinction determines conversion policy. An AST leaf can become a headed
S-expression with a value atom. A term variable uses a question-prefixed atom
under the term reader's conventions. An e-graph extraction chooses one finite
representative from an equality class. Each conversion may discard information
or impose a convention. A sound application documents the convention where it
crosses the boundary, rather than assuming all tree-shaped objects are lossless
views of one another.

## The callable layer

C++ templates preserve the concrete types of pipe stages, rewrite predicates,
rewrite transformers, and many visitor handlers. Their compositions become
tuples or recursively nested types. The compiler can see the callable's type,
but a callable may still capture pointers, allocate memory, or throw an
exception. Static dispatch means the function target is statically represented;
it does not promise that the function's body is pure or cheap.

Some interfaces deliberately erase callable types. `Parser<T>` contains a
`std::function<ExpectedResult<T>(ParsecInput&)>`. `Lazy<T>` stores a
`std::function<T()>`. Tasks and several PEG callbacks use analogous wrappers.
These choices simplify ownership and allow recursive or heterogeneous
arrangements, at the cost of indirect calls and possible allocation. A
performance argument about the CRTP base cannot be transferred automatically
to these wrappers.

The D port often preserves concrete callable types where C++ uses an erased
wrapper. Generic lambdas can be bound through alias template parameters and a
`StaticCallable` adapter. This is one reason mechanically translating C++
syntax into D misses the actual design. The public role can remain the same
while the callable representation and instantiation cost change significantly.

## The parsing layer

There are three distinct parsing arrangements in the header. Ordinary parser
combinators pass a mutable cursor through callables and return typed semantic
values or errors. Commitment distinguishes a mismatch that can try another
branch from a failure that should stop ordinary choice. PEG combinators wrap
these operations with speculative behavior, lookahead, and span reporting.
The application controls how deeply these parsers are composed.

`PEGDefinition`, despite its broad name, is primarily an ordered tokenizing
driver in this snapshot. Individual rules are patterns compiled into a small
sequence of atoms. They are not arbitrary recursive PEG productions written
as text. The driver tries rules at the current offset, accepts the first
success, invokes actions, and advances. The surrounding application can build a
recursive parser over the resulting tokens, but that parser is an additional
layer rather than a hidden feature of the pattern syntax.

`CFG` takes explicit context-free productions and a vector of token strings.
Its Earley chart supports nullable productions and left recursion, builds an
AST, and reports a failure frontier. The tokenizer is outside this interface.
This separation permits the same grammar to consume tokens produced by a PEG
definition, a byte regex, or an application-specific lexer. Choosing among the
interfaces depends on desired semantics, not on which name sounds most general.

## The transformation layer

`RewriteSet` applies a tuple of AST rules in bottom-up passes. A rule is a
predicate plus a transformer, not a declarative pattern with built-in binding.
The pass cascades all rules at a node and repeats while a rule fires, subject
to a pass limit. That makes it useful for normalization where committing to a
single replacement is acceptable. It also means identity rules and cycling
rules can exhaust the budget without an explicit convergence report.

`TermRewriteSystem` is more formal about positions and steps. Its rules use
first-order matching and substitution. One step chooses a redex using outermost
or innermost traversal and returns the rewritten term together with the rule
index and position. Normalization reports either normal form or a step limit.
An application interested in reduction traces can use this granularity rather
than reconstructing it from whole-tree AST passes.

`EGraph::saturate` retains equal alternatives instead of choosing one rewrite
path. The cost is additional storage, matching work, and congruence rebuilding.
Explicit iteration, node, and application limits make resource control visible.
Extraction then selects a minimum-node representative. These three engines
share the idea of replacing or equating expressions, but their termination
criteria, observability, and retained information differ substantially.

## Boundaries and external policy

The serialization and I/O adapters are intentionally thin. A serializer
forwards a value and an output object to a user backend; the backend decides
the format. An I/O adapter completes byte spans using a user backend's transfer
counts; the backend decides how bytes reach storage or a peer. Borrowing the
backend avoids imposing a single ownership model. It also requires the caller
to maintain the backend's lifetime.

Preprocessing follows the same principle. Includes are resolved through a
callback instead of implicit filesystem access. Script directives invoke a
callback instead of choosing a scripting runtime. The optional Lua adapter
connects a user-owned Lua state to that protocol and restores the stack after
execution. The toolkit supplies an integration point, while the application
defines search paths, source identity, environment access, and lifecycle.

That policy separation is a useful architectural boundary. It allows the same
parser and semantic logic to run in an editor, command-line tool, test harness,
or service without changing the representation layer. It does not eliminate
the need to specify behavior at the boundary. A short read, invalid transferred
count, missing include, or script error still needs a defined interpretation.

## Reading an operation from end to end

Consider a configuration file containing a numeric port. Preprocessing first
produces expanded source. A tokenizing grammar recognizes words, digits,
punctuation, and ignored whitespace. Its callbacks copy spans into owned tokens.
A domain parser checks assignment structure. A semantic validator checks the
port's range. Finally, a temporary settings object is published only after all
checks succeed. No single feature implements that entire sequence, but each
boundary has a small, testable contract.

Now consider an arithmetic optimizer. An S-expression reader produces syntax;
rule validation checks variable discipline; an e-graph stores alternatives;
saturation applies trusted equalities; extraction chooses a representative;
and an interpreter compares behavior over a test domain. The same architecture
distinguishes representation, transformation, and meaning, although the
concrete types are different. The case studies make these sequences executable
instead of treating them as architectural slogans.

## Extension strategy and failure discipline

Extend the toolkit at the narrowest stable boundary. A custom feature tag is
appropriate when a host needs a repeated convenience interface. A free helper
is appropriate when the operation should work without a host. A user backend
is appropriate when external policy differs. A new representation is justified
when existing representations cannot preserve a required distinction, such as
typed literal payloads or multiple derivations of an ambiguous grammar.

Before adding machinery, establish the failure contract. Does an operation
return an optional, a tagged result, an error envelope, or throw? Does failure
leave the input cursor unchanged? Can it leave partial nodes in a graph? Does
a callback run before the operation is fully committed? These questions
determine whether two components can be composed safely. Similar names and
matching template syntax are not enough to establish compatibility.

The source snapshot contains real examples of why this discipline matters.
The same-type C++ `Result` is not usable through its type-based queries, even
though construction syntax exists. The task runner inherits that problem.
Predicate members express a recognizable Boolean algorithm but instantiate the
wrong wrapper specialization for their new lambda. A source-based book must
distinguish the intended abstraction from the behavior that a compiler accepts.
Doing so teaches a transferable reading skill: follow the actual call path,
instantiate the important operation, and test the boundary rather than
trusting an overview comment alone.

## A small architectural experiment

The following complete example uses two independently usable layers. The host
provides a tree factory, while the namespace-level reader performs interchange.
The feature choice does not control access to the reader.

```cpp
#include "DSLtk.hpp"
#include <cassert>
struct Language : dsl::DSL<Language, dsl::AST> {};
int main() {
  auto tree = Language::make_leaf<"number">(42);
  auto syntax = dsl::ast_to_sexpr(tree);
  assert(syntax.dump() == "(number 42)");
  assert(dsl::sexpr_to_ast(syntax) == tree);
}
```

Its value is not the number of lines saved. It exposes where the compile-time
choice ends: the factory name contains a static tag, but `tree` is an ordinary
runtime `ASTNode`. Conversion then operates on that value without knowing the
host type. This is the basic architectural pattern repeated throughout DSLtk:
static composition makes an interface convenient, while explicit runtime
objects preserve the information that later stages need.
