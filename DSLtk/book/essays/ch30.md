## A protocol adapter should not choose a file format

Serialization and byte I/O are often coupled in small programs. A function
opens a file, formats a value, writes bytes, and returns a Boolean. That is
convenient until the same language implementation must run against an in-memory
test buffer, a network connection, or an editor's virtual document. DSLtk
separates two contracts: codecs interpret values and formats, while I/O
backends transfer bytes. The adapters connect these contracts without choosing
their external policy.

`Serializer<Backend>` borrows a backend and forwards `serialize(value, output)`.
`Deserializer<Backend>` forwards `deserialize<T>(input)`. Their concepts check
whether those expressions are well formed. They do not require JSON, binary
records, streams, exceptions, or a particular result type. `decltype(auto)`
preserves the backend's returned value or reference category. The adapter is
therefore a generic protocol wrapper rather than a complete serialization
framework.

This design puts format ownership where it belongs: in the domain codec.
A query AST, a physical quantity, and a network frame need different formats
and validation rules. The library cannot infer a compatible wire schema from
the fact that all three are C++ objects. It supplies a consistent call shape
while leaving the meaning of a serialized artifact explicit.

## Borrowing is a lifetime contract

The adapters hold references to their backends. Constructing an adapter does
not copy the backend, extend its lifetime, or create shared ownership. A
backend allocated on a local stack must outlive every adapter call that uses
it. If the backend owns a file, socket, or memory buffer, its own lifetime
and mutation rules determine what subsequent operations can observe.

Returning a backend reference through `decltype(auto)` can preserve useful
fluent interfaces or zero-copy views, but it can also expose borrowed data.
The caller should read the backend's return contract rather than assume the
adapter always produces an owned object. Forwarding faithfully is a strength
only when the forwarded protocol is documented. An adapter cannot repair an
ambiguous ownership model hidden in the backend.

A concept likewise checks syntax rather than complete semantics. A backend
with a `serialize` member satisfies the expression requirement even if it
emits an incompatible format or ignores the value. Tests should therefore
exercise round-tripping, rejection of malformed input, and format stability
where those are required. Compile-time protocol checking is the first layer
of evidence, not the last.

## The byte-transfer contract

An `IOBackend` provides `read` into a mutable byte span and `write` from a
const byte span. Each returns a count convertible to `size_t`. Counts may be
smaller than the requested span. A zero read denotes end of input under this
protocol. The adapter rejects a count larger than the span, because such a
count would make cursor advancement invalid and conceal a broken backend.

Partial transfer is an ordinary condition. A file abstraction, compressed
stream, or socket-like backend may produce fewer bytes than requested without
meaning the whole operation failed. `read_exact` and `write_all` implement the
completion loops that callers would otherwise repeat. Each iteration passes
only the remaining suffix of the span and advances by the count actually
transferred.

A zero count has different meanings in the two completion loops. During an
exact read, it means the requested amount cannot be completed and produces an
unexpected-EOF error. During write-all, it means no progress and produces a
write-progress error. The loop does not spin indefinitely waiting for a backend
that keeps returning zero. This behavior follows directly from the protocol's
synchronous progress contract.

## Why nonblocking I/O needs another decision

Some operating-system APIs distinguish EOF from a temporary would-block
condition. DSLtk's basic count protocol does not encode that distinction as a
separate return value. A backend cannot return zero for would-block and expect
`read_exact` to wait correctly, because zero is interpreted as EOF. It must
either block until progress, throw or otherwise signal a condition outside
this count path, or be driven by an application layer designed for incremental
nonblocking transfer.

This is not a defect in exact-read logic. It is a boundary between two
different abstractions. A synchronous byte source promises that a call can
report progress or final exhaustion. An event-driven source may require
registration, polling, and resumption. Combining them requires an explicit
adapter policy; merely using a network socket as the backend type does not
turn a synchronous completion loop into an asynchronous operation.

The same reasoning applies to cancellation and deadlines. The library loop
does not own a clock or cancellation token. A backend can honor such policy
inside its transfer operation, or an application can build a bounded driver
around smaller transfer requests. The abstraction should make the policy
visible rather than let callers infer guarantees from a familiar method name.

## Seek and tell are optional capabilities

The I/O adapter exposes `seek` and `tell` only when the backend supports the
corresponding operations. A memory buffer and a regular file can naturally
offer a position. A stream of incoming messages may not support arbitrary
seeking. Constraining optional operations avoids forcing every backend to
invent meaningless behavior for capabilities it does not possess.

Position itself also needs a unit. The basic adapter forwards the backend's
operation; the application should document whether positions are byte offsets
in an underlying file, offsets in a decompressed view, or another logical
address. A seekable codec can use these operations for checkpoints, but a
nonseekable source may need buffering if transactional parsing requires
rewinding. The binary stream case study chooses a buffered input precisely
to make its cursor checkpoint well defined.

## A short-transfer backend is a useful test double

An in-memory backend that transfers every requested byte in one call can
hide bugs in completion loops. A better test backend deliberately limits reads
to two bytes and writes to three. The caller then has to handle partial
progress even for a short record. The binary case study's `ShortBuffer`
implements exactly this behavior and routes `BinaryStream::save` and `load`
through the real adapter.

The test remains deterministic. It does not need a real socket, timing, or a
particular filesystem. The payload after round-trip must match exactly, and
the final cursor must identify complete consumption. A second backend can
return an invalid count or zero during write-all to exercise the adapter's
contract enforcement. These tests verify the boundary rather than merely
calling the same loop on ideal inputs.

```cpp
#include "DSLtk.hpp"
#include <cassert>
struct Buffer {
  std::vector<std::byte> data;
  std::size_t pos = 0;
  std::size_t write(std::span<const std::byte> in) {
    auto n = std::min(in.size(), std::size_t{2});
    data.insert(data.end(), in.begin(), in.begin() + n);
    return n;
  }
  std::size_t read(std::span<std::byte> out) {
    auto n = std::min({out.size(), data.size() - pos, std::size_t{1}});
    std::copy_n(data.begin() + pos, n, out.begin());
    pos += n;
    return n;
  }
};
int main() {
  Buffer backend;
  dsl::IO io(backend);
  std::array<std::byte, 4> data{std::byte{1}, std::byte{2}, std::byte{3}, std::byte{4}};
  io.write_all(data);
  std::array<std::byte, 4> received{};
  io.read_exact(received);
  assert(received == data && backend.pos == 4);
}
```

The backend's `pos` is always maintained within its data size, so subtraction
used to compute remaining input is valid. A public backend with arbitrary
external cursor mutation would need an additional guard. Small examples
should still state the invariants on which their arithmetic depends.

## Format validation belongs above byte completion

Successfully transferring a record does not make it a valid record. The
codec may need to check a magic value, version, length, field vocabulary, and
checksum. Those checks belong above I/O completion because they interpret
the bytes. Conversely, a valid record format does not ensure that the
transport delivered all its bytes. Keeping these concerns separate produces
clearer errors and independently testable components.

Length fields illustrate the interaction. The transport can deliver any
number of bytes, while the format may limit a payload to sixty-four bytes.
The decoder should validate the declared length before allocating or reading
an unbounded amount. `BinaryStream::load` also has an overall input limit,
but that does not replace per-record validation. A buffer limit and a field
limit constrain different aspects of the operation.

The serializer should likewise validate before emitting a partial record
when practical. If it writes a header and then discovers an invalid payload,
the output may already contain an unusable prefix. The binary case study
checks the payload vocabulary and length before writing. More complex codecs
may stage a complete record in a temporary buffer, then publish it through
write-all. That is a format-level transaction built from the simpler byte
protocol.

## Extending a backend without changing the language

Once a language implementation uses the codec and I/O boundaries consistently,
changing storage does not require changing its AST or grammar. A file backend
can wrap `std::ifstream` and `std::ofstream`; a test backend can use vectors;
a compressed backend can expose decompressed bytes. Each must translate its
underlying failure and progress behavior into the declared protocol.

The price of this flexibility is discipline about what the adapter promises.
It forwards operations, validates transfer counts, and completes spans. It
does not supply schema evolution, object graphs, compression, encryption,
authentication, asynchronous scheduling, or ownership extension. Those may
all be appropriate application facilities, but they should appear as explicit
layers with their own contracts. The reference examples below show how little
code is needed when those boundaries are kept narrow.
