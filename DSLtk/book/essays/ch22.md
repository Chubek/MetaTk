## Progress is a precondition of C++ repetition

The supplied C++ zero-or-more combinator loops while its child succeeds. It
does not compare the old and new cursor after a successful iteration. Repeating
a parser that succeeds without consuming input can therefore loop indefinitely.
An optional parser and a lookahead parser are common sources of such empty
success. Place them inside a sequence that consumes, rather than directly
under repetition, or implement a checked application helper.

The D `ManyParser` explicitly checks this condition and reports a committed
`<non-empty repetition>` failure. That is a behavioral difference, not merely
a different operator spelling. A portable grammar should establish progress
regardless of whether the implementation diagnoses its absence.

Backtracking restores a cursor, not arbitrary application state. An action
that appends to a vector or writes to a stream is not undone when `try_parse`
rewinds input. Parse into a temporary semantic value and publish it only after
the enclosing production succeeds. This transactional pattern also underlies
the configuration case study.
