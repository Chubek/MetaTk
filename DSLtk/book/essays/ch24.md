## A pipeline of activities rather than a pipeline of values

A pipe stage transforms one value into another. A task represents a named
activity that can inspect and update shared state. Reading a source file,
parsing it, checking its declarations, and emitting an artifact form a task
pipeline even when the intermediate values have different structures and
lifetimes. The name of each stage is useful independently of its result: it
provides an audit point and an entry in a diagnostic report.

DSLtk's task API makes this arrangement explicit with three small types.
`Task` contains a name and a callable. `TaskChain` contains an ordered vector
of tasks and a continuation policy. `TaskState` contains a map of named results
and a suspension flag. The design is intentionally synchronous. There is no
thread pool, dependency scheduler, future, coroutine, or automatic retry
hidden in the word pipeline. Calling the driver executes ordinary callables
in vector order on the caller's thread.

This smallness is educationally valuable. A build system may need a complex
scheduler, but it still has to answer the same elementary questions: when is a
result recorded, what happens after failure, how is partial progress observed,
and who owns the state? By making these decisions visible in a few lines,
DSLtk provides a model that can be inspected before an application grows a more
elaborate orchestration layer.

## The snapshot limitation must come first

The C++ task API fixes both success and error payloads to `std::string`.
Its driver calls `Result<std::string,std::string>::is_err()`. As Chapter 20
explained, that query uses a type-based operation on a variant with duplicate
types and fails to instantiate. A normal call to `dsl::run(state, chain)` is
therefore rejected in the supplied C++ snapshot. The companion header probe
records this failure. The implementation can be studied, but it cannot be
presented as an unqualified working C++ recipe.

The D task API uses a result type with an explicit discriminator and supports
the identical payload types. It supplies a working realization of the intended
driver. For C++ applications in this book, a small local task model with a
distinct error type demonstrates the same policy while leaving the studied
header untouched. This separation preserves provenance: the library's design
and an application's compatibility implementation are not the same artifact.

## The public records

| Type | Stored data | Role |
|---|---|---|
| `TaskState` | Named string results and `suspended` | Shared execution record |
| `Task` | `name` and `run_fn` | One named operation |
| `TaskChain` | `tasks` and `policy` | Ordered plan |
| `TaskPolicy` | Stop or continue on error | Driver continuation decision |

In C++, `Task::run` simply invokes the stored `std::function`. It does not
insert its result into the state map. That insertion belongs to the chain
driver, which uses `insert_or_assign`. Consequently, a task can be called
directly without creating a history entry, and a task can inspect the results
that earlier driver calls have already recorded. This distinction matters
when tests call a task directly: they are testing the operation, not the
driver's bookkeeping.

The state map is keyed by task name, not by an execution identifier. Running
two tasks with the same name overwrites the earlier entry. Running the same
chain again can overwrite every entry from the previous run. This is a latest
result table, not an append-only event log. An application that needs history
should create a separate trace containing sequence numbers, timestamps, and
outcomes rather than inferring history from a map that intentionally replaces
values.

The map also does not establish a dependency graph. A task named `parse` may
choose to read an entry named `source`, but the driver does not know that
relationship. If the expected entry is missing, the task must diagnose it.
This is the principal trade-off of the string-keyed design: it is flexible and
easy to extend, but the compiler cannot prove that every dependency is present
or that a payload has the intended interpretation.

## Composition and the run loop

`Task | Task` constructs a two-element chain with the default stop-on-error
policy. `TaskChain | Task` appends another task to a copied or moved chain.
The second overload preserves the existing policy. This is ordinary value
composition; no execution happens merely because the pipe expression is
constructed. A chain can be stored, inspected, and run later.

The driver executes one task, records its result, and then checks the
continuation conditions. Under `StopOnError`, an error stops the loop. Under
`ContinueOnError`, the loop proceeds unless the state is suspended. Because
recording precedes the checks, the task that failed or suspended execution
still has a visible result. That ordering is a useful invariant for a user
interface: the last activity is inspectable even though later activities were
not attempted.

The variadic arguments accepted by the C++ `run` template are ignored by its
implementation. Passing an extra context object does not forward it into each
task. Context must be captured by the callable or placed in an application
state object. A permissive signature can look like an extension mechanism
without implementing one; reading the function body prevents that mistaken
assumption.

## An executable C++ model with distinct error payloads

The following program is application code. `Step` and `State` deliberately
have local names rather than pretending to repair `dsl::Task`. The program
uses the actual DSLtk result type in its supported distinct-payload form and
makes the driver policy visible.

```cpp
#include "DSLtk.hpp"
#include <cassert>
#include <iostream>
struct Error { std::string message; };
using Outcome = dsl::Result<std::string, Error>;
struct State {
  std::unordered_map<std::string, Outcome> results;
  bool suspended = false;
};
struct Step {
  std::string name;
  std::function<Outcome(State&)> action;
};
void execute(State& state, const std::vector<Step>& steps, bool stop_on_error) {
  for (const auto& step : steps) {
    auto result = step.action(state);
    state.results.insert_or_assign(step.name, result);
    if ((stop_on_error && result.is_err()) || state.suspended) break;
  }
}
int main() {
  std::vector<Step> steps{
    {"read", [](State&) { return Outcome::from_ok("18"); }},
    {"parse", [](State& state) {
      auto it = state.results.find("read");
      if (it == state.results.end() || it->second.is_err())
        return Outcome::from_err({"no source"});
      auto text = it->second.unwrap();
      if (!dsl::StaticRegex<"[0-9]+">::matches(text))
        return Outcome::from_err({"digits required"});
      return Outcome::from_ok(text);
    }},
    {"validate", [](State&) { return Outcome::from_err({"rejected by policy"}); }},
    {"report", [](State&) { return Outcome::from_ok("completed reporting"); }}
  };
  State stopped, continued;
  execute(stopped, steps, true);
  execute(continued, steps, false);
  assert(stopped.results.contains("validate"));
  assert(!stopped.results.contains("report"));
  assert(continued.results.contains("report"));
  std::cout << stopped.results.size() << ' ' << continued.results.size() << '\n';
}
```

The output is `3 4`. The test establishes more than successful execution: it
checks that the failed step is recorded, that stop-on-error prevents a later
step, and that continue-on-error allows that later step. These are the
observable policy properties that matter to a caller. Repeating the loop's
implementation in a test would provide less independent evidence.

Notice that the parser step checks the predecessor's existence before
extracting its value. Continue-on-error does not magically produce successful
prerequisites. If an application chooses to continue, each downstream task
must distinguish an absent prerequisite from a failed prerequisite and decide
whether it can proceed. Reporting and cleanup tasks are often able to proceed;
semantic analysis usually cannot proceed without a valid parse tree.

## Suspension and conditional activities

`suspend(state)` sets a Boolean flag. The driver checks that flag after the
current task has run. It does not retain an instruction pointer or a next-task
index. Calling `run` again starts a new traversal of the chain, not a
continuation from the suspension point. Even a state already marked suspended
can enter the loop and run a task before the post-task check. Applications that
need resumable execution should store an explicit cursor alongside the chain.

This is an example of why operational timing belongs in documentation.
The words stop and suspend can suggest stronger behavior than a Boolean flag
actually supplies. A user interface may want to stop before the next task,
whereas a cooperative task may inspect cancellation inside a long operation.
The supplied driver only makes one of those decisions: whether to leave its
loop after the current call has completed.

`upon(state, event, task)` calls the event predicate without arguments and runs
the task when that predicate is true. It is a synchronous conditional call,
not event registration, a listener loop, or a subscription. The predicate can
capture state to inspect earlier results. Its result is evaluated at the
moment `upon` is called. In the C++ snapshot, the implementation also uses
map indexing with the non-default-constructible result type, another reason to
treat this path as implementation study rather than a working recipe.

## Result policy versus exception policy

A task's explicit error result is different from an exception thrown by the
callable. The run loop does not wrap arbitrary exceptions into a result.
If a task throws, normal loop execution stops through stack unwinding before
the driver records that task's returned result, because no result was
returned. Earlier map entries remain present. An application needs a policy
for whether exceptions are fatal implementation errors or expected external
failures to convert into its error payload.

The appropriate boundary is usually close to the operation that knows the
context. A file-reading task can catch an I/O exception and attach a filename.
A parser task can convert a structured parse failure into a message with a
source location. A generic driver should not flatten every possible failure
into an uninformative string unless that loss of structure is acceptable to
its consumers.

The string-result design also raises a data-model question. If later stages
need an AST, storing its diagnostic dump is not equivalent to storing the
tree. The dump may not be a lossless format, and reparsing it introduces
additional work and ambiguity. A serious compiler pipeline often uses a
typed application state for artifacts and a separate map for human-readable
stage outcomes. The small DSLtk task records can inspire the latter without
dictating the former.

## The D implementation as a comparison

The D task types express the same ordered-driver design with delegates and
an associative array. Its result type distinguishes success from error using
an explicit Boolean, so identical string payloads are valid. The module's
embedded tests exercise stop-on-error behavior and conditional activities.
This is an instructive case where the secondary implementation clarifies the
intended abstraction while exposing a defect in the primary implementation.

It is still important to compare exact behavior rather than assume all
differences vanish. Callable captures, result copying, and associative-array
lookup have language-specific semantics. A D class captured by a delegate
remains a reference object; a copied C++ value may own independent state or
may still contain borrowed pointers. The same high-level task diagram can
therefore have different ownership consequences in the two implementations.

## When to outgrow the small driver

A linear chain is appropriate when execution order is naturally fixed and
the program mostly needs clear stage boundaries. It becomes awkward when
independent tasks should run concurrently, tasks have typed dependencies,
results should be cached across runs, or a suspended computation must resume
at an exact point. Those needs justify additional scheduling structure.
They do not justify obscuring the simple policies already established here.

Before replacing the driver, preserve its useful contracts in the new design:
record outcomes at a defined time, distinguish not-run from failed, identify
dependencies explicitly, and make continuation policy observable. A graph of
activities can use `DirectedGraph` for dependency analysis, but graph edges
alone do not execute tasks. Scheduling, concurrency control, and artifact
ownership are application mechanisms that must be designed separately.

Finally, keep verification focused on policy boundaries. A task pipeline test
should include a successful chain, a failing predecessor, a continuation
policy that reaches an independent reporting task, duplicate names if they
are permitted, and a suspension request. These cases reveal the execution
contract far more effectively than testing only that a vector of functions
can be iterated. The source's compactness makes such tests easy to design;
the snapshot defect makes them necessary before claiming a working interface.
