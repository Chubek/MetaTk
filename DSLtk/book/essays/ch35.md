## Graph identity is different from tree position

An AST child is identified naturally by its path from a root. A general graph
node can have several predecessors, belong to a cycle, or be disconnected
from the current root. Its identity therefore cannot be reduced to one tree
position. DSLtk's directed graph assigns integer handles to nodes and edges
and stores adjacency separately from the payload values.

The implementation is a directed multigraph. Parallel edges, self-loops,
isolated nodes, and cycles are legitimate structures. This matters for
language tooling: two dependency edges can represent different reasons for
the same relationship, and a control-flow graph can contain loops. An
application that wants a simple acyclic graph must enforce those additional
constraints rather than assume the container does so automatically.

Node and edge payload types are template parameters. Their defaults are
strings, which makes examples easy to print. A real application might use
instruction records, source locations, dependency kinds, or term labels.
Algorithms operate on handles and adjacency, so the payload meaning remains
application policy. DOT rendering accepts label callbacks to turn richer
payloads into display text.

## Stable slots and retired storage

Nodes and edges occupy vectors of optional slots. Adding an entity appends a
new slot and returns its index. Removing an entity resets its slot rather than
renumbering later entries. A surviving handle therefore retains its numeric
identity across unrelated removals. Removed handles are not recycled, so an
old removed ID cannot accidentally become the identity of a newly added node
in the same graph instance.

Stable IDs are not stable references. Growing a vector can move its elements,
and mutation can invalidate references returned by accessors. Retain handles
across graph changes and reacquire payload references afterward. This is a
common but important distinction: the logical identity can be stable while
the physical address of its storage is not.

Retired slots also have a cost. Whole-graph enumeration scans storage to find
live entries, so a graph with a long mutation history can scan many dead
slots even if few nodes remain. The design favors simple stable identity over
automatic compaction. A compaction feature would need a deliberate handle
remapping contract, because silently renumbering IDs would break external
references to the graph.

## Adjacency lists preserve edge identity

Each node records incoming and outgoing edge IDs. An edge records its source,
target, and payload. Adding an edge updates both endpoint lists. Removing an
edge removes its ID from those lists and retires the edge slot. Removing a
node first removes all incident edges, then retires the node. These operations
maintain consistency between global edge records and local adjacency.

Successor and predecessor queries derive node IDs from those edge lists.
Parallel edges can therefore produce repeated neighbor IDs. A traversal's
visited set prevents repeated expansion of a node, but a raw successor list
is not necessarily a mathematical set. Applications counting dependencies or
indegree should decide whether they mean edges or distinct neighboring nodes.
The two counts differ in a multigraph.

Insertion order is preserved in adjacency lists. Depth-first search pushes
successors in reverse so that popping the stack visits them in the original
left-to-right order. This gives deterministic traversal for a fixed mutation
history. It does not define a unique graph-theoretic order independent of how
the graph was built. Tests should either rely deliberately on insertion order
or compare order-insensitive properties.

## Redirect means retarget incoming uses

`redirect(from,to)` changes the target of every incoming edge of `from` to
`to`. It preserves those edge IDs and payloads, appends them to the target's
incoming list, and clears the source node's incoming list. It does not move
the outgoing edges of `from`, and it does not remove either node.

This operation is particularly useful for shared-term reduction. Incoming
edges represent uses of a subexpression; redirecting them makes all those
uses refer to a replacement. The old redex can then be removed, which removes
its outgoing edges. The distinction between redirect and remove allows the
caller to control when old structure is retired and whether any other roots
still need to be considered.

A self-loop and a redirect into an existing descendant deserve careful
reasoning. General graphs permit cycles, so retargeting can create or change
cyclic structure. The container is not a term-graph validity checker. A
domain layer that requires an acyclic representation must reject or avoid
operations that violate that requirement before relying on recursive
tree-expansion functions.

## Breadth-first and depth-first traversal

Breadth-first search uses a work queue and discovers nodes in increasing
unweighted distance from a chosen root. A visited set ensures each reachable
node is expanded once even when there are cycles or parallel paths. It is
appropriate for reachability layers and provides the basis for an unweighted
shortest path.

Depth-first search uses an explicit stack of node IDs paired with an expanded
flag. In preorder, a newly encountered node is emitted immediately. In
postorder, the algorithm schedules a completion entry after scheduling the
successors, so the node is emitted after its reachable descendants have been
processed. The visited set cuts cycles; the completion flag encodes the
return action that a recursive implementation would keep on the call stack.

An explicit stack avoids dependence on C++ recursive call depth for these
graph traversals. It still uses memory proportional to the traversal's
working state, and nodes may be pushed more than once before duplicate pops
are discarded. The useful guarantee is bounded expansion through the visited
set, not that each edge causes exactly one stack insertion in every ordering.

## Shortest paths and topological order answer different questions

`shortest_path` uses breadth-first discovery and a parent map. On reaching
the target, it reconstructs a path containing both endpoints. If the target
is unreachable, it returns an empty optional. The path is shortest by edge
count, not by payload-defined weight. A graph whose edge payload stores a
cost does not automatically turn this algorithm into Dijkstra's algorithm.

Topological sorting instead seeks an ordering in which every directed edge
goes from an earlier node to a later node. Such an order exists only for an
acyclic graph. The implementation considers the entire graph, including
disconnected nodes, and throws if a cycle prevents completion. A successful
topological order is useful for dependency scheduling, but it does not run
the associated activities.

A graph can have several valid topological orders. A test should verify that
each edge respects the returned order and that every live node appears once,
rather than require one incidental sequence unless deterministic insertion
order is itself part of the application contract. This distinction makes
tests robust to harmless algorithmic changes.

## Strongly connected components expose cycles structurally

Strongly connected components partition nodes so that every pair within a
component is mutually reachable. DSLtk uses an iterative two-pass strategy:
obtain a finishing order, then traverse the reversed graph in that order.
The resulting components can reveal recursive declaration groups, cyclic
dependencies, or loops in a symbolic relation.

A component containing one node is not necessarily acyclic: it may contain
a self-loop. An application diagnosing cycles should inspect internal edges
as well as component size. Contracting each component into one node produces
an acyclic condensation graph, a useful next step for ordering mutually
recursive groups. Building that graph is application code; the component
routine returns the partition rather than a complete scheduler.

The graph algorithms share the same identity and adjacency contracts. They
do not interpret payloads and do not validate domain-specific edge kinds.
A control-flow analysis may need to distinguish exceptional edges from normal
edges, while a dependency analysis may treat optional edges differently.
Filter or construct the graph appropriate to the analysis rather than assume
every stored edge has the same semantic role.

## DOT is a serialization format, not a rendering service

`to_dot` emits a complete directed Graphviz document as text. Internal names
such as `n0` identify nodes, while payload-derived strings become labels.
The container does not launch Graphviz or write a file implicitly. A caller
can save the text and render it with a separate tool, or display it in a
diagnostic interface that understands DOT.

Label quoting escapes double quotes, backslashes, and line breaks. Tabs are
retained literally in this implementation; unsupported control characters
are rejected. This is a specific output policy, not a promise that every
arbitrary byte string is a valid display label. Rich payloads should use label
callbacks that deliberately choose a readable and bounded textual summary.

DOT output preserves isolated nodes and parallel edges. Omitting either would
misrepresent the graph, even if a simple tree-like example happened not to
show the difference. When comparing exported graphs, remember that labels are
display data and internal IDs are graph-local handles. A label repeated on
two nodes does not make them the same node.

## A dependency example with executable invariants

```cpp
#include "DSLtk.hpp"
#include <cassert>
#include <iostream>
int main() {
  dsl::DirectedGraph<> graph;
  auto read = graph.add_node("read");
  auto parse = graph.add_node("parse");
  auto check = graph.add_node("check");
  graph.add_edge(read, parse, "source");
  graph.add_edge(parse, check, "tree");
  auto order = graph.topological_sort();
  assert(order.size() == 3);
  auto path = graph.shortest_path(read, check);
  assert(path && path->size() == 3 && path->front() == read && path->back() == check);
  assert(!graph.shortest_path(check, read));
  std::cout << graph.to_dot("Dependencies");
}
```

The unreachable reverse path verifies edge direction, while the successful
path verifies both endpoints and length. Adding a back edge would create a
cycle and should make topological sorting fail. Removing an unrelated node
would not renumber the surviving handles. These are useful boundary tests
because they exercise the graph's contracts rather than only its happy-path
construction syntax.

## The C++ and D ownership distinction

The C++ graph is a value type whose vectors are copied when the graph is
copied. The D graph is a reference class; assigning its reference aliases
the same mutable object. A port that copies a C++ graph to run a speculative
transformation cannot assume a D assignment creates the same isolation.
It must establish an explicit clone or rebuild policy if independent state
is required.

Neither implementation synchronizes mutation. Concurrent algorithms need an
application-level ownership or locking strategy, and traversals should not
assume adjacency remains unchanged while another thread mutates it. The
container's simple sequential model is a useful foundation for graph-based
language tools precisely when these ownership boundaries remain explicit.
