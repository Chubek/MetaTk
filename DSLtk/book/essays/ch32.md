## Two regular-expression engines, two contracts

The header contains a small recursive `pattern` matcher and a separate
`StaticRegex` implementation. They should not be selected interchangeably.
The small matcher is useful for simple whole-token classification with its
limited syntax. `StaticRegex` compiles a richer byte-oriented expression into
a Thompson NFA and exposes whole-input, longest-prefix, and leftmost-search
operations. The shared word pattern does not imply shared syntax or matching
policy.

The static in `StaticRegex` refers to the pattern and compiled program. The
pattern is a `FixedString` template argument, and constexpr compilation builds
an array of states. A failed compilation triggers a static assertion. Matching
ordinary runtime input still executes a state-set simulation and uses runtime
working storage. This is a deliberate split between validating a fixed
recognizer early and applying it repeatedly to later byte sequences.

Byte semantics are especially important. The alphabet is all 256 byte values,
including NUL. Character classes and ranges refer to bytes, not Unicode code
points or grapheme clusters. A dot can consume one byte of a multibyte UTF-8
character. This behavior is appropriate for binary protocols and ASCII-like
token languages, but a Unicode-aware lexer needs additional decoding and
classification policy.

## Thompson fragments make composition explicit

The compiler represents a partially built automaton as a fragment with a
start state and a list of unpatched exits. A literal contributes one consuming
state. Concatenation patches the first fragment's exits to the second's start.
Alternation creates a split state whose branches enter the alternatives.
Repetition patches exits back to a split that chooses another iteration or
an exit. These local operations compose into a complete automaton without
requiring a separate backtracking program for each pattern shape.

The state vocabulary includes byte, wildcard, class, split, empty, beginning
anchor, end anchor, and accept. Consuming states advance the input; split,
empty, and anchor states are traversed through epsilon closure when their
conditions permit it. A class state stores a 256-entry membership array.
This simple representation favors clarity over a compact bitset encoding.

The program capacity is derived from the pattern length. The compiler marks
the program invalid if construction exceeds capacity or encounters malformed
syntax. Grouping, alternation, classes, ranges, negation, repetition, anchors,
and escapes are parsed by small recursive-descent functions. Captures,
backreferences, counted repetition, and Unicode properties are not part of
the implemented language. A static pattern should be written to this exact
grammar rather than copied unexamined from another regex dialect.

## The NFA simulation remembers all active possibilities

At a given input position, the matcher has a set of active states. Epsilon
closure follows nonconsuming transitions until consuming or accepting states
are reached. For the next byte, every active consuming state that accepts it
contributes its successor to the next closure. Deduplication prevents the
same state from being expanded indefinitely through epsilon cycles.

This strategy differs fundamentally from a recursive backtracking engine
that explores one path and later returns to alternatives. A Thompson matcher
keeps alternatives active together. For a fixed pattern, prefix matching has
work proportional to input traversed times the program's state count, subject
to the implementation's state-set bookkeeping. It avoids exponential
backtracking caused by repeatedly rediscovering the same alternatives.

The matcher records every accepting position it reaches and returns the last
one for a prefix query. Thus `prefix` implements longest accepted prefix from
the requested start. The result is an absolute end offset, not the number of
bytes consumed. Subtract the supplied start to obtain length. This distinction
becomes visible as soon as matching begins somewhere other than offset zero.

## Whole matching, prefix matching, and search

`matches` requires a prefix match beginning at zero whose end equals the
input size. It is the natural operation for validating a whole field or token.
`prefix` is appropriate for consuming the next token at a known cursor.
`search` tries successive start positions and returns the first start with a
match, using the longest prefix at that start. The policy is therefore
leftmost-longest within the supported regular language.

The search implementation repeatedly invokes prefix matching. It does not
perform one specially optimized unanchored NFA pass. A pattern that scans far
before failing at many successive starts can cause quadratic input work even
though each individual prefix simulation has the more predictable NFA cost.
Performance claims should distinguish these entry points rather than apply a
single generic linear-time slogan to every operation.

Anchors are evaluated against the supplied byte sequence. Beginning means
position zero, and end means the input's size. Starting a prefix search at a
nonzero offset does not redefine beginning to mean that offset. This matters
for tokenizers that reuse one whole-buffer span and advance a cursor. If a
caller instead supplies a sliced span, the anchors naturally refer to that
slice's boundaries. The choice of input view is therefore part of the
recognition contract.

## A binary stream is a buffer plus a cursor

`BinaryStream` owns a vector of bytes and a public cursor. Constructing from
a span copies the bytes. `read(count)` returns a borrowed span into the
owned vector and advances the cursor after checking bounds. `write(span)`
appends bytes; it does not overwrite at the read cursor. Treating it as a
bidirectional file with one seek position would therefore be misleading.

The write implementation stages the input span in a temporary copy before
appending. This makes appending a span borrowed from the same stream safe
against reallocation during insertion. Earlier borrowed views can still be
invalidated by later storage changes. A decoded field that must survive
subsequent writes should be copied or represented by offsets whose owner
remains explicit.

The public cursor makes integration easy but permits invalid states if callers
assign it arbitrarily. The read operation checks that the cursor is within
storage and that the requested count fits the remaining bytes. Application
code should preserve this invariant rather than depend on every subsequent
operation to repair a malformed cursor. A checkpoint-and-restore decoder can
save a valid cursor and restore exactly that value after failure.

## Integer fields need an explicit byte order

`read_integer<T>` and `write_integer<T>` operate on unsigned integral types
and accept a byte-order argument. The implementation assembles or separates
bytes using shifts. It does not reinterpret a potentially unaligned pointer
as an integer and does not depend on host endianness. This makes the wire
order visible at the call site.

Unsigned wire fields are often the simplest foundation even when a domain
value is signed. The protocol can specify how signed values are encoded, then
the application can convert after range checks. Floating-point wire formats
need their own representation contract as well. The existence of generic
integer methods should not be stretched into a claim that the stream knows
how to serialize arbitrary arithmetic objects.

The default byte order is little endian. A protocol that requires big endian
must request it consistently on both writing and reading. Matching mistakes
can hide in round-trip tests if both encoder and decoder make the same wrong
assumption. A useful protocol test also compares the encoded bytes against an
independent expected sequence. The final case study documents its header
layout and length-field order for exactly this reason.

## Regex token reads must make progress

`next<Regex>` applies a longest-prefix match at the current cursor and returns
the matched byte span. No match leaves no token. A successful empty match is
rejected, because repeatedly requesting tokens without advancing would make
a consumer loop forever. This explicit progress check differs from the
ordinary C++ parser repetition combinator, which lacks that guard in the
supplied snapshot.

A token regex can therefore be syntactically valid but unsuitable for
`next`. For example, a star-only pattern can accept an empty sequence. The
regular language is legitimate, yet the token-stream contract requires a
nonempty accepted token. Distinguishing recognizer validity from consumer
progress is a recurring theme throughout parser and stream design.

```cpp
#include "DSLtk.hpp"
#include <cassert>
int main() {
  std::string source = "abc_7";
  auto bytes = std::as_bytes(std::span(source.data(), source.size()));
  dsl::BinaryStream stream(bytes);
  auto token = stream.next<"[a-z][a-z0-9_]*">();
  assert(token && token->size() == source.size() && stream.eof());
  dsl::BinaryStream wire;
  wire.write_integer<std::uint16_t>(0x1234, dsl::ByteOrder::Big);
  assert(wire.bytes[0] == std::byte{0x12} && wire.bytes[1] == std::byte{0x34});
  assert(wire.read_integer<std::uint16_t>(dsl::ByteOrder::Big) == 0x1234);
}
```

The token is a view into the stream, while the source string was copied into
the stream at construction. The integer assertions check both wire bytes and
decoded value. These are separate properties: a round trip alone could not
prove that the chosen byte order matched a published protocol.

## Loading and saving do not define framing

`load` reads through an `IO` adapter in fixed-size chunks until zero read
signals EOF. It enforces an overall byte limit, defaulting to 64 MiB. `save`
uses write-all to transfer the owned buffer. These operations are convenient
for complete bounded inputs. They do not parse a message length, distinguish
several records, or decide whether EOF is allowed halfway through a protocol
message.

Length-prefixed framing belongs in a codec above the stream. A decoder reads
the fixed header, checks the declared payload length, obtains that many bytes,
and validates any trailer. If multiple frames share a connection, it repeats
that process while preserving the cursor between frames. If the transport is
incremental and EOF is not final, a separate buffering policy must distinguish
incomplete data from a malformed complete record.

The connection between regexes and binary streams is therefore practical
rather than universal. Regexes are good for fixed byte vocabularies and local
token patterns. Explicit integer fields and domain checks are better for
length-dependent structure. The final case study uses both: a regular language
validates a payload identifier, while explicit fields define the frame.

## Choosing a cost model for a real lexer

A fixed pattern still has a state count and working storage. A lexer with
many separately instantiated patterns can increase compile time and binary
size. A search over a large buffer can revisit prefixes. A byte class with
wide membership is still a byte class, not a Unicode category. These facts do
not make the implementation unsuitable; they identify the measurements and
contracts that matter for deployment.

Begin with correct whole-field and token semantics, then measure representative
inputs. Include failing inputs as well as successful ones, because a long
nonmatching suffix can dominate search cost. Keep the source pattern near
the field or token contract it implements. A static regex is most effective
when its fixed language is small, deliberate, and repeatedly reused, rather
than an opaque string copied from another engine's documentation.
