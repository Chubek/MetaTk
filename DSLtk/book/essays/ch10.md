## Two constraints established by the implementation

The `when` factory takes an **auto non-type template argument**. A pattern key
must therefore be an object, for example
`dsl::when<dsl::pattern<"[0-9]+">{}>(handler)`. Passing only the pattern type
does not satisfy the template parameter even though that spelling appears in
older comments. Pattern objects are empty structural values; their static
`matches` member supplies the actual recognition operation.

There is also a return-type constraint stronger than the common-type alias in
`MatchTable` first suggests. The table creates `optional<RetT>` for a common
return type, but each clause's `try_invoke` parameter names an optional of that
handler's exact `invoke_result_t`. An optional of a merely convertible type
does not bind to a reference to another optional specialization. Use identical
concrete return types for all handlers. Void handlers and reference results
are not supported by this optional-result arrangement.

These restrictions do not prevent useful dispatch. They define where to put
conversions: normalize each handler's output inside the handler, and pass a
structural pattern value at construction. The clause order remains part of
the language semantics, and the key comparisons still happen at runtime when
the caller supplies a runtime key.
