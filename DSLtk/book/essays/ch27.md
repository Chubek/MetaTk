## Recognition is only the beginning of semantics

A tokenizer tells an application that a span looks like a number, identifier,
or punctuation token. A language implementation must then decide what that
span means and how it relates to neighboring spans. The distinction is easy to
miss when a callback is named a semantic action: attaching an action to a
recognizer does not, by itself, implement expression precedence, associativity,
scope, or type checking. It merely supplies a point at which application code
can observe a successful match.

DSLtk's `PEGMatch` records that observation. It contains the source view,
begin and end offsets, rule pointer, channel, user pointer, line, column, and
ignored status. The matched `value` is a `std::string_view` into the original
input. Its lifetime follows the input buffer, not the match record. Keeping a
copy of the record does not copy the underlying text. A durable token or AST
should copy the text it needs or retain an explicit owner for the whole source.

This chapter builds a small expression language while keeping each role
visible. The PEG definition recognizes lexical pieces. An application parser
checks the token sequence. A semantic stack or left-fold operation constructs
an `ASTNode`. The tree's interpreter would be another application layer. This
arrangement is more honest and easier to debug than calling the whole program
a grammar and leaving its semantic responsibilities implicit.

## The match record as a borrowed observation

| Field | Meaning | Lifetime or interpretation |
|---|---|---|
| `value` | Matched text | Borrows the source buffer |
| `begin`, `end` | Half-open byte interval | Relative to the input passed to the driver |
| `rule` | Originating rule | Can be invalidated by C++ rule-vector growth |
| `channel` | Routing category | A value copied into the observation |
| `user_data` | Untyped application pointer | No automatic owner or allocator |
| `line`, `column` | One-based location | Computed by scanning source bytes |
| `ignored` | Ignore-channel marker | Does not universally suppress callbacks |

The `length()` member returns `end - begin`. A valid match therefore has a
half-open interval consistent with its view. Offsets are useful for reporting
where a token originated, but they do not encode an entire source map. If the
input was preprocessed, the offsets refer to expanded text. Reconstructing a
location in an included or macro-containing original file requires additional
mapping information that this record does not provide.

The user pointer is especially easy to overinterpret. `void*` permits an
application to attach an address, but it does not provide a semantic-value
stack, a typed variant, or persistence between independent matches. The
default match construction initializes the pointer to null. If an action
writes it, later consumers must already agree on the pointee type and
lifetime. For this chapter's examples, capturing an owned token vector is
clearer than routing data through an untyped slot.

## Why token text should usually be copied

Consider parsing a temporary string returned by a file-reading function.
An action that stores `m.value` in a vector of views seems efficient, but
those views become invalid when the temporary string is destroyed. The AST
may survive much longer, perhaps until code generation or an editor query.
Copying a short token spelling into `std::string` is often a small price for
a simple ownership contract. Later optimization can retain a shared source
buffer and store offsets instead, provided that owner is explicit.

The tree factories already favor owned textual payloads. A call to
`leaf<"number">(token.text)` stores a string representation inside `ASTNode`.
That makes the resulting tree independent of the token vector. The tree still
does not know that the payload is a valid number; the application must either
validate before construction or ensure the evaluator handles conversion
failure. A lexical class and a semantic numeric range are different contracts.

## A deliberately small expression grammar

Our language accepts one or more unsigned decimal tokens separated by plus
signs, with optional whitespace between them. It has only one operator, so
precedence is not an issue. Associativity is a left fold: `1+2+3` becomes
`add(add(1,2),3)`. This makes the resulting tree shape predictable and provides
a concrete example of semantics that token recognition alone cannot supply.

The PEG definition has three rules: whitespace, decimal digits, and plus.
Whitespace has the ignore channel and no action. Number and plus actions append
owned tokens. The parser then checks that a number appears first and that
remaining tokens occur as plus-number pairs. A leading plus, trailing plus,
two adjacent numbers, or an unknown character is rejected. Publishing the
root only after those checks makes the operation transactional at the tree
boundary.

```cpp
#include "DSLtk.hpp"
#include <cassert>
#include <iostream>
struct Token { bool number; std::string text; std::size_t offset; };
dsl::ASTNode parse_sum(const std::string& source) {
  std::vector<Token> tokens;
  auto grammar = dsl::create_peg_definition();
  grammar.add_rule<"[ \t\r\n]+">().channel = dsl::PEGIgnoreChannel;
  grammar.add_rule<"[0-9]+">([&](dsl::PEGMatch& m) {
    tokens.push_back({true, std::string(m.value), m.begin});
  });
  grammar.add_rule<"+">([&](dsl::PEGMatch& m) {
    tokens.push_back({false, std::string(m.value), m.begin});
  });
  auto recognized = grammar.parse(source);
  if (!recognized.ok()) throw std::invalid_argument("unrecognized token");
  if (tokens.empty() || !tokens[0].number)
    throw std::invalid_argument("expected first number");
  auto root = dsl::leaf<"number">(tokens[0].text);
  for (std::size_t i = 1; i < tokens.size(); i += 2) {
    if (i + 1 == tokens.size() || tokens[i].number || !tokens[i + 1].number)
      throw std::invalid_argument("expected plus and number");
    root = dsl::node<"add">(std::move(root),
                            dsl::leaf<"number">(tokens[i + 1].text));
  }
  return root;
}
int main() {
  auto tree = parse_sum("1 + 2 + 3");
  assert(tree.dump() == "(add (add (number 1) (number 2)) (number 3))");
  bool rejected = false;
  try { (void)parse_sum("1 +"); }
  catch (const std::invalid_argument&) { rejected = true; }
  assert(rejected);
  std::cout << tree.dump() << '\n';
}
```

The program does not retain rule references across insertion. It configures
the whitespace channel immediately, then grows the rule vector without
depending on any previous element address. The callbacks capture the token
vector by reference, whose lifetime covers the local grammar's use. Those
two ownership choices avoid the most common C++ lifetime mistakes in this
small subsystem.

## From a left fold to a semantic stack

A left fold is enough for one operator. A stack becomes useful when the input
contains explicit nesting or postfix operations. On a number, push a leaf.
On a completed binary operation, pop the right operand and then the left,
construct an operator node in that order, and push the result. Operand order
matters even if the first demonstration uses commutative addition. The same
stack protocol should work correctly for subtraction and division.

For infix expressions with several precedence levels, the application needs
an additional mechanism such as recursive descent, precedence climbing, or an
operator stack. None is automatically created by the PEG definition's regular
patterns. A token action should generally append a token rather than guess
whether a reduction is now appropriate. Keeping recognition and reduction
separate makes precedence errors visible in one place.

An explicit semantic stack also needs invariants. Every reduction must have
enough operands; each pop must preserve the intended left-to-right ordering;
and successful completion should leave exactly one root. A stack containing
two unrelated operands is not a successful parse merely because all tokens
were recognized. These final-state checks turn a stream of actions into a
language implementation with a clear acceptance condition.

## Callback timing and transactional construction

The tokenizing driver invokes actions as matches are found. A later lexical
failure does not undo earlier appends. In the example, that is harmless
because the vector is local and the function throws before returning a tree.
If the same actions mutated a global symbol table, earlier mutations would
remain after failure. Recognition success at one token is not a transaction
commit for the whole source.

The same concern appears with parser combinators. `try_parse` restores an
input cursor on failure; it cannot restore arbitrary memory written by an
action. A speculative branch that increments a counter or publishes a symbol
can leave observable effects even when another branch is eventually selected.
Pure semantic values are easiest to compose: create a candidate value in the
branch, then transfer it to durable application state only after acceptance.

For large trees, the temporary need not mean copying everything twice.
Move the completed root into its owner after validation. Alternatively, use
an arena whose entire allocation region can be discarded after failure, but
recognize that such an arena is application infrastructure, not supplied by
`ASTNode`. The important contract is all-or-nothing publication, not a
particular memory-management technique.

## Diagnostics that preserve the failing phase

A lexical error says no rule recognized the next byte. A grammatical error
says the recognized tokens have an invalid arrangement. A semantic error
says a structurally valid construct has an invalid meaning, such as a numeric
literal outside an allowed range. Collapsing all three into `parse failed`
wastes information that the implementation already has.

The example keeps offsets in each token, even though its short exception
messages do not print them. A fuller implementation would attach the
unexpected token's offset to a syntax error and the literal's offset to a
conversion error. It would retain the source owner until diagnostics are
formatted. This provides useful reporting without coupling the AST to every
lexical implementation detail.

Line and column calculation also has a cost model. The PEG helper scans the
input to the desired position. Repeatedly calculating locations for many
tokens can revisit prefixes. An editor-oriented application may instead build
a table of line starts once and translate offsets with a binary search. That
optimization belongs at the diagnostic boundary and can be introduced without
changing the grammar's meaning.

## Comparing the three semantic-value paths

Ordinary `Parser<T>` makes the semantic value part of the parser type. A
successful parser returns `T`, so composition can combine values explicitly.
This is natural when the application is already comfortable expressing
recursive structure in C++ functions and parser combinators. Error handling
and commitment are visible in the returned envelope.

PEG token actions instead expose a span and let the callback decide where
to put its meaning. This is convenient for token collection, instrumentation,
and routing by channel. It is less direct for a deeply nested typed result
because the driver does not manage an application semantic stack. The
application must define that stack or a second parser layer.

Earley CFG parsing goes further in a different direction. It takes explicit
productions and constructs an AST from completed chart items. Nonterminal
names become inner-node tags and terminals become token leaves. The
application then applies semantic visitors or conversions to that syntax
tree. The algorithm handles recognition structure, but it still does not know
the domain meaning of a node named `Expr`.

| Approach | Semantic carrier | Application responsibility |
|---|---|---|
| Typed parser combinators | `ExpectedResult<T>` | Construct and combine typed values |
| PEG token actions | Match spans and captured state | Parse token structure and own results |
| Earley CFG | Automatically built `ASTNode` | Interpret nonterminal and token tags |

Choosing between these paths is a design decision, not a hierarchy of
quality. A simple configuration syntax benefits from an ordered tokenizer and
a small validator. A grammar with left recursion may fit Earley naturally.
A typed embedded parser may prefer combinator values throughout. The common
requirement is that each transition preserves the distinctions needed by the
next stage.

## Extending the example without hiding its contracts

To add parentheses, first extend the token vocabulary. Then define a parser
for a parenthesized expression that requires both delimiters and recursively
builds an inner expression. To add multiplication, give it a tighter
precedence level than addition. To add names, decide whether the AST stores
only a spelling or a resolved binding. Each extension changes a different
contract; none should be implemented by making a number regex increasingly
complicated.

The five case studies reuse this principle. Configuration copies token text
and validates settings before publication. The query language builds semantic
ASTs directly because it is embedded. Equality saturation keeps an
interchange representation until extraction. Binary framing copies a payload
only after the framing checks identify its exact span. The reusable lesson is
ownership and phase separation: a successful match is evidence about bytes,
while a successful language construct is evidence about structure and meaning.
