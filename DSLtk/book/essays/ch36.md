## Terms make variable binding part of the representation

An AST tag can be interpreted however an application chooses. A first-order
term has a more specific structure: a variable, or a function symbol with an
ordered sequence of argument terms. A nullary function is a constant. This
model supports matching and unification because the representation tells the
algorithm which positions may bind and which symbols must agree literally.

DSLtk's `Term` stores the symbol, argument vector, and a variable flag.
Variables use bare names internally; the S-expression printer adds a question
mark for external notation. A quoted question-prefixed atom is a literal
function symbol rather than a variable. The parser therefore depends on the
quotedness preserved by `SExpr`, not only on atom text.

There is no global signature table declaring each function's arity. The same
symbol can appear with different argument counts in different terms. Matching
and unification require both symbol and local arity to agree, but they do not
validate a language-wide type discipline. A typed term language can add a
signature and sort checker before using these generic algorithms.

## One-way matching and two-way unification

Matching asks whether a pattern can describe a subject by assigning values
to variables in the pattern. Subject variables are subject data, not additional
unknowns for the matching algorithm to solve. If a pattern variable occurs
twice, both occurrences must receive structurally equal subjects. For example,
`pair(?x,?x)` matches `pair(a,a)` but not `pair(a,b)`.

That repeated-variable consistency check is not the occurs check. The occurs
check belongs to unification, where variables on either side can be solved.
It prevents assigning a variable to a term containing that same variable,
such as solving `?x = f(?x)` with a finite first-order substitution. Confusing
these checks obscures the difference between verifying a consistent match
and preventing an infinite self-referential solution.

Unification maintains a work list of term pairs. It substitutes known
bindings into each pair, skips equal terms, orients a variable to one side
when possible, and either binds it or decomposes matching function symbols
into argument pairs. New bindings are applied to existing binding values so
the resulting substitution can be applied simultaneously to make the two
original terms equal.

## Simultaneous substitution has a precise boundary

`substitute` replaces a variable by its mapped term when a binding exists.
It does not recursively reapply the whole substitution inside a freshly
inserted binding. This is simultaneous substitution. If a hand-written map
contains `x -> y` and `y -> a`, substituting `x` once yields `y`, not necessarily
`a`. The unifier composes its bindings so its own returned environment has
the property needed for the solved equation.

This distinction matters when applications build substitutions directly.
A recursive normalization of a substitution map is a separate operation and
needs cycle handling. A map containing `x -> y` and `y -> x` should not make
a generic substitution function recurse forever. Keeping insertion and
recursive processing separate is a clear way to avoid that ambiguity.

Term positions are vectors of child indices. The empty position denotes the
root. `at` follows the indices through bounds-checked argument access, while
`replaced` constructs a value copy with the selected subterm changed. A
position therefore refers to the current tree shape, not a stable identity
across arbitrary rewrites. A trace should record the term or step context in
which a position was meaningful.

## Directed rules and strategy

A `TermRule` contains a name, left side, and right side. Validation forbids
a variable-only left side and requires every right-side variable to appear
on the left. These conditions make matching and instantiation well defined.
They do not establish termination, confluence, or semantic correctness of
the rule set. Those are properties of the chosen rules and domain.

`rewrite_once` searches according to an outermost or innermost strategy and
tries rules in insertion order at each candidate position. Outermost tries a
node before its arguments. Innermost descends into arguments before trying
the node itself. Both use left-to-right argument order, so the selected redex
is deterministic for a fixed term and rule order.

Strategy can change whether a term reaches a normal form within a budget,
which intermediate terms appear, and even whether an unrestricted reduction
would terminate. A rule that discards an argument may let an outermost
strategy avoid reducing a divergent subterm. An innermost strategy may insist
on reducing that subterm first. The strategy is therefore a semantic and
operational choice, not merely a performance toggle.

## Bounded normalization reports what it established

`normalize` repeatedly requests one rewrite and counts applied steps. When
no rewrite is available, it reports normal form. When another rewrite is
available but the allowed step count has been reached, it reports a step
limit. Reaching normal form exactly on the last permitted step still reports
normal form, because the next reducibility check finds no further step.

An identity rule can consume the budget because it remains applicable even
when its replacement is structurally equal to the input. A cycle of rules
can do the same. The budget guarantees a bounded number of applied rewrites,
not a proof that the system is terminating. A language optimizer should inspect
the stop reason and decide whether a partial result is acceptable.

The report's explicit status is stronger than the AST rewrite set's silent
pass truncation. It is one reason to choose the term engine when reduction
traces and limits are part of the application interface. The two engines
still have different pattern models: term rules bind variables structurally,
while AST rules invoke arbitrary user predicates and transformers.

## Sharing changes the unit of reduction

`TermGraph` represents term structure in a directed graph whose edge payloads
record argument indices. Insertion can share structurally identical subterms.
Two occurrences in a tree may therefore become two incoming edges to one
graph node. Rewriting that shared node updates all incoming uses, so one
graph rewrite can correspond to several tree-occurrence rewrites.

This is the central benefit and semantic responsibility of graph reduction.
For pure symbolic terms, sharing avoids repeated work and can greatly reduce
storage. For expressions with effects or evaluation-count-sensitive behavior,
sharing may change meaning. The application must decide whether the term
language admits such sharing before using graph reduction as a drop-in
replacement for tree reduction.

The graph matcher binds variables to node IDs and checks repeated occurrences
through structural node equality. Its equality procedure tracks pairs already
compared, so sharing and cycles do not cause that comparison to loop forever.
Other operations have different assumptions. In particular, `to_term` expands
children recursively and has no general cycle guard; it should be used only
when the reachable graph can be unfolded finitely.

## Applying a graph rewrite and retaining roots

Applying a rule instantiates its right side, redirects incoming edges from
the selected redex to the replacement, and removes the old node. If the
redex was the chosen root, the returned step supplies a new root ID. The
caller must use that returned root rather than continue treating the removed
ID as live. Other externally retained roots and handles need similar care.

An identity-like graph rule is particularly hazardous in this snapshot if
instantiation returns the redex itself, because removal still follows
redirection. Use genuinely replacing, well-founded rules for the executable
graph examples and inspect the implementation before admitting arbitrary
rules into a persistent shared graph. A rule structurally acceptable to the
tree validator is not automatically safe for every graph mutation pattern.

Unreachable old subterms can remain after reduction. `collect_garbage` computes
reachability from the supplied roots and removes other nodes. The root set
must include every value the application intends to keep. Forgetting one
live external root can delete its structure, while including obsolete roots
can retain unnecessary storage. Garbage collection is explicit precisely
because the container cannot discover all application-held handles.

## A semantic comparison between tree and graph forms

For a pure arithmetic identity system, normalize a tree and reduce a shared
graph built from the same term. Compare their final unfolded terms when both
reports establish normal form. Do not require identical step counts: shared
redexes make those counts describe different units of work. A graph with
sharing disabled can provide another useful comparison point.

Also compare meaning through an independent evaluator when possible. Two
different normal forms can still be semantically equal, and a syntactically
smaller result can still be wrong. Structural comparison verifies one
property, evaluator comparison verifies another, and stop reports establish
an operational property. Together they provide a much clearer account of a
reduction engine than a single printed before-and-after string.

The reference examples below introduce the public operations and D spellings.
D uses `function_` because `function` is a language keyword, and its graph

secondary to the shared logical contracts: variable discipline, simultaneous
substitution, strategy, bounded steps, and explicit ownership of graph roots.
