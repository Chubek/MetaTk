## A small interchange language with a large architectural role

S-expressions give DSLtk a common notation for trees, rewrite rules, and
grammars. Their usefulness comes from making nesting explicit while keeping
the reader small. Parentheses describe lists, atoms describe indivisible
spellings, and quoted atoms preserve data that would otherwise collide with
syntax. The notation does not assign domain meaning to a list. `(add a 0)`
becomes arithmetic only when an application or symbolic subsystem chooses to
interpret its head and children that way.

The C++ `SExpr` record contains an atom flag, a text string, a vector of child
expressions, and a quoted flag. It is not a discriminated union. Both text and
child storage exist in every object, and the flag identifies which field is
meaningful. The named factories establish consistent states, while public
fields make direct construction possible. Application code should prefer the
factories unless it deliberately needs to manipulate representation details.

The D module supplies the corresponding record and reader. Its mutable child
storage is copied through the port's value semantics. The important shared
contract is not binary layout: it is the distinction between atom and list,
the order of list items, and the preserved quotedness of atoms. These are the
properties on which the rule and grammar readers depend.

## Quotedness carries meaning beyond printing

Many readers treat quotes as purely lexical decoration. DSLtk retains whether
an atom was quoted because downstream consumers use that distinction. In
rewrite patterns, an unquoted `?x` denotes a variable. A quoted `"?x"` denotes
literal data with the same textual spelling. In CFG notation, quoted atoms in
a production are terminals, while unquoted atoms are nonterminals. Erasing
quotedness after tokenization would make both interfaces ambiguous.

The atom factory also quotes text automatically when necessary for readable
output. Empty text, whitespace, parentheses, a double quote, semicolon, or
backslash require quoting. A plain question mark does not by itself require
it. Consequently, constructing `SExpr::atom("?x")` does not escape a would-be
pattern variable; use the explicit quoted argument when literal intent matters.
The factory's convenience and the downstream language's semantics meet at
exactly this point.

Defaulted equality compares quotedness as well as payload and structure.
Thus quoted `"a"` and bare `a` are different `SExpr` values. That is a useful
property for grammar notation, but it may surprise an application that wants
all atom spellings normalized. Such an application should define a separate
normalization or semantic equality operation instead of assuming the record's
structural equality ignores lexical distinctions.

## The reader's operational model

The reader owns no input. It keeps a string view and a byte cursor. Before
reading an expression it skips whitespace and semicolon comments. It then
selects one of three paths: a parenthesized list, a double-quoted atom, or a
bare atom. Lists recurse until the closing parenthesis. Quoted atoms decode
the supported escapes. Bare atoms consume a run until a delimiter is reached.
The algorithm is recursive descent over this tiny grammar.

The depth argument bounds recursive nesting. The implementation rejects a
read at a depth greater than 512 rather than allowing arbitrarily deep source
nesting to consume the process stack. This is a bound on reader recursion,
not a universal tree-depth bound for all programmatically constructed
`SExpr` values. The printer and later algorithms have their own recursion
patterns and should be considered separately when an application accepts
untrusted or extremely deep generated structures.

Errors include the byte position and a descriptive reason. An unterminated
list, unfinished escape, unknown escape, or unexpected closing delimiter is a
syntax failure. The reader does not recover by inventing a missing delimiter
or discarding the rest of a line. An editor that needs recovery should build
that policy above the reader rather than assuming a successful prefix parse
is available after every failure.

## Exactly one expression versus a sequence

`parse_sexpr` requires exactly one top-level expression. Empty input and two
adjacent expressions are both rejected by that entry point. This is the right
contract for a single optimizer input or a single term passed to a function.
`parse_sexpressions` returns all top-level expressions and permits an empty
sequence. It is the natural entry point for a file of rewrite rules.

The difference is more than convenience. A caller that expects one expression
should not silently accept the first expression and ignore trailing data.
Doing so would make a malformed configuration or rule file appear valid.
The explicit cardinality check makes the acceptance condition visible at the
API boundary. It also means that a list containing several items is still
one expression; top-level count and child count are independent quantities.

Single-quote Lisp reader syntax is not supported. The bytes `'x` form an
ordinary bare atom whose text includes the quote. There is no automatic
desugaring to `(quote x)`, no dotted-pair notation, and no numeric atom type.
Numbers remain strings until a consumer interprets them. These omissions
keep the interchange reader independent of any particular Lisp evaluator.

## Printing is a serialization policy

The `dump` operation writes lists with one space between items and writes
atoms either bare or double quoted. Within quoted atoms, newline, carriage
return, tab, double quote, and backslash receive supported escape spellings.
This representation is intended to be readable by the same reader. It is
more suitable for interchange than `ASTNode::dump`, which simply prints
payload text without a quoting discipline.

A printer need not preserve the original whitespace or comment layout to
preserve the expression. Reading `(add   a ; comment\n 0)` and printing it can
yield `(add a 0)`. That is structural round-tripping, not source-format
round-tripping. If a refactoring tool needs comments and exact spacing, it
must retain a concrete-syntax representation or source spans in addition to
the abstract expression.

Likewise, direct mutation can create unusual records that the printer
normalizes. A caller can set `quoted` false on an atom containing spaces, but
the printer still recognizes that quotes are necessary. A read-print-read
test should therefore begin with well-formed factory-produced values when it
expects exact record equality. Public representation fields are useful, but
they make invariant discipline an application responsibility.

## AST conversion is a convention, not an isomorphism

The bridge converts a leaf to a headed list containing tag and value, and an
inner node to a headed list containing tag and converted children. Reading
back a two-item headed list whose second item is an atom creates a leaf.
A bare atom becomes an AST leaf tagged `atom`. These choices are practical
for the toolkit's examples, but they do not provide a one-to-one mapping among
all possible AST and S-expression values.

For example, an S-expression list can have a list as its first item, while
the AST bridge requires a literal atom head to become a tag. An AST has a
leaf discriminator that can distinguish an empty leaf from a zero-child
inner node, while a naive diagnostic spelling may obscure that distinction.
Quotedness has a role in the interchange model that ordinary AST payload
strings do not retain in the same way. A conversion should therefore be
chosen for a known representation subset.

An optimizer that already operates on headed S-expressions should often keep
that representation throughout equality saturation. Converting to AST is
useful when a visitor or an existing domain interpreter expects AST tags.
Perform the conversion at that boundary, and state which expression shapes
the consumer accepts. Repeatedly converting between representations without
a clear contract creates opportunities for silent information loss.

## Rule notation and variable discipline

The rule reader recognizes `(rewrite name lhs rhs)`, `(= lhs rhs)`, and
`(=> lhs rhs)`. The longer form supplies a descriptive name. The shorthand
forms use their operator text as the name. Names support reporting; they do
not change the mathematical meaning of a rule. A rule's search orientation
is still from left pattern to right expression even though applying it to an
e-graph records an equality relation.

Variables occupy complete term positions. The head of a compound e-graph
term must be a literal atom, not a pattern variable or a list. Every variable
on the right must also occur on the left, because matching the left supplies
the environment used to instantiate the right. Rejecting an unbound right
variable at rule-loading time is much better than failing halfway through
saturation when a substitution lookup cannot find it.

The notation's equality sign does not certify the rule. A user can write a
mathematically false equality that is structurally valid. The reader checks
syntax and binding discipline, not semantic truth. The application must
restrict rules to laws valid in its domain. Integer identities, floating-point
identities, and expressions with side effects have different valid law sets.
This responsibility becomes central in the saturation case study.

## A useful round-trip experiment

```cpp
#include "DSLtk.hpp"
#include <cassert>
#include <iostream>
int main() {
  auto literal = dsl::SExpr::atom("?x", true);
  auto variable = dsl::SExpr::atom("?x");
  assert(literal != variable);
  assert(!dsl::is_pattern_variable(literal));
  assert(dsl::is_pattern_variable(variable));
  auto expression = dsl::SExpr::list({dsl::SExpr::atom("message"),
                                    dsl::SExpr::atom("line one\nline two")});
  assert(dsl::parse_sexpr(expression.dump()) == expression);
  assert(dsl::parse_sexpressions("; empty file\n").empty());
  std::cout << expression.dump() << '\n';
}
```

This test separates textual equality from structural equality and verifies a
reader-printer contract on escaped data. It also checks that an empty rule-file
style input is a valid sequence. Extending it with malformed escapes and
unterminated lists exercises rejection behavior without pretending that the
reader performs error recovery. The detailed reference material below builds
on these distinctions and connects them to the e-graph workflow.
