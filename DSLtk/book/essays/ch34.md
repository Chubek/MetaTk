## Preprocessing is a language stage with observable policy

A preprocessor rewrites source before the parser sees it. That can make a DSL
more convenient by providing constants, reusable fragments, conditional
sections, and included sources. It can also make diagnostics and reproducibility
harder if the transformation's inputs are hidden. DSLtk therefore exposes
include and script operations as callbacks and keeps the macro table visible
on the preprocessor object.

The implementation is a deliberately limited preprocessor, not a complete
implementation of the C or C++ preprocessing standard. It recognizes object
and function macros, a subset of integer condition expressions, include
directives, conditionals, explicit errors, and script directives. Token
pasting, stringification, variadic macros, and the full standard preprocessing
token grammar are outside its supplied contract. A DSL should specify which
subset it intends its users to rely on.

Two entry points make the stage separation explicit. `expand` performs macro
expansion on text. `process` handles logical lines and directives as well as
ordinary expansion. Passing a directive string to `expand` does not mean it
will be interpreted like a complete source file. Conversely, a returned script
string is macro-expanded according to the implementation's script path, not
automatically reprocessed as an arbitrary new directive file.

## Lexical state protects quoted text and comments

Macro expansion scans characters and recognizes identifiers outside quoted
strings and comments. A macro named `PORT` should replace the identifier
`PORT`, but not the same bytes inside a quoted message. Quoted strings are
copied with their escapes, and comments are preserved rather than treated
as places to expand identifiers. This is a small lexical discipline, not a
blind global search-and-replace operation.

Block-comment state persists in the preprocessor object. A comment can begin
on one line and end on another, so processing each physical line with an
independent stateless substitution would be incorrect. The same state must be
maintained through inactive conditional regions. Even when their expanded text
is discarded, those lines are scanned with macro names disabled so that a
comment opened in skipped text is not forgotten.

Persistent state also means object reuse deserves thought. A preprocessor
retains its macros and lexical state between calls. That can be useful when
processing related fragments, but a caller expecting independent files should
establish whether it wants a fresh object or deliberate shared definitions.
The object is mutable and supplies no synchronization for concurrent calls.

## Expansion depth and disabled names solve different problems

When expanding a macro, the implementation temporarily disables that name
along the recursive expansion path. A self-referential definition such as
`SELF` replaced by `SELF` therefore terminates rather than recursively
expanding forever. Mutual recursion is similarly controlled by the active
disabled-name set. The resulting text can still contain the disabled name;
termination does not imply the name disappeared.

The maximum expansion depth bounds recursive work more generally. A long
chain of distinct macro names can avoid immediate self-reference while still
requiring many recursive expansions. The depth limit provides an operational
boundary for such chains. It is not a proof that every expansion produces a
small output, because a macro can duplicate a large argument or replacement.
Applications concerned about output size need a separate output-budget policy.

The distinction is similar to graph reduction limits. A cycle guard prevents
one class of nontermination; a depth or step budget limits work; an output
size limit constrains storage growth. Combining these concerns into one vague
recursion limit hides which resource is actually controlled.

## Function macros parse arguments before substitution

A function-like invocation requires a following opening parenthesis after
optional whitespace. The scanner tracks nested parentheses and skips quoted
strings while locating commas at the outer argument level. This permits a
macro argument to contain a parenthesized expression without splitting it
at every internal comma. Unterminated invocation and argument-count mismatch
produce errors rather than silently supplying missing arguments.

Arguments are expanded before their parameter names are substituted into the
replacement text. Parameter substitution replaces identifier occurrences
outside quoted strings. This is a specific expansion policy that users should
learn from the implementation, especially if they arrive with expectations
from a full C preprocessor. Similar-looking surface syntax does not guarantee
identical behavior for nested invocations and unusual punctuation.

Zero-parameter macros receive special handling so the empty text between
parentheses does not become one spurious argument. Duplicate parameter names
and malformed parameter lists are rejected when a definition is processed.
These checks keep the later substitution map meaningful: each parameter name
should denote one argument, and every invocation should satisfy the declared
arity.

## Conditions form a small expression language

The conditional evaluator supports logical negation, parentheses, `defined`,
comparisons, conjunction, disjunction, and signed integer spellings with
hexadecimal detection. An object-like macro can be evaluated recursively as
a conditional expression. An undefined name, a disabled recursive name, or
a function-like macro in this context contributes zero under the implemented
rules.

Arithmetic operators are not part of this expression grammar. A condition
that looks natural in C, such as adding one to a macro value before comparison,
can therefore be rejected as unsupported text. The evaluator requires the
whole condition to be consumed. This is preferable to accepting a numeric
prefix and silently ignoring the rest of an expression that the user assumed
was meaningful.

The evaluator is an implementation-specific expression parser, not a complete
model of C's conditional-expression evaluation. In particular, callers should
not rely on general C short-circuit behavior to hide malformed unsupported
subexpressions. Keep conditions within the documented grammar and test their
complete spellings. The configuration case study uses simple numeric macro
substitution rather than stretching this condition language.

## The conditional stack tracks branch history

Each active conditional level records whether its parent is active, whether
some branch has already been taken, whether the current branch is active,
and whether an else has appeared. `#elif` can activate only if the parent
is active and no earlier branch was taken. `#else` selects the remaining
case. An unmatched or duplicate branch directive is rejected.

This state is necessary because nested conditionals are not merely independent
Boolean tests. A true condition inside an inactive parent must remain inactive.
An else branch after an already selected branch must remain inactive even if
its own text has no condition. The stack records the control history needed
to interpret those directives correctly.

At the end of processing, a nonempty stack means an unterminated conditional.
Publishing output from such an input would make acceptance depend on an
accidental end-of-file convention. The explicit error keeps source structure
well defined. Applications should likewise avoid committing partially
preprocessed configuration when processing throws midway through a file.

## Includes are resolved, not opened implicitly

The include callback receives a path spelling and returns source text. The
library does not choose search directories, normalize paths, open files, or
distinguish a system include from a local include beyond recognizing the
allowed delimiters. Quoted and angle-bracket forms both reach the user resolver
with their delimiters removed.

This is useful for deterministic tests and virtual sources. A resolver can
serve a map of named strings, an editor buffer, or a project database. It can
also attach its own diagnostic context when a requested source is missing.
The preprocessor recursively processes the returned text under an include-depth
limit. A resolver that needs cycle-specific diagnostics can track an include
stack in addition to that depth bound.

Macro expansion applies to the include directive's path text before resolution.
That permits a macro to select a source name, but it also means the final
resolved source is an input to the language build. Reproducible tooling should
record the resolved names and source contents or hashes rather than treating
the top-level filename as the only relevant input.

## Script callbacks and the optional Lua bridge

`#script` supplies a language name and code string to a user callback;
`#lua` supplies the language name implicitly. The callback returns text.
The basic preprocessor does not create a runtime or decide which facilities
the script may access. It only defines the bridge between a directive and
generated source text.

When `DSLTK_ENABLE_LUA` is defined, the C++ header includes the Lua headers
and provides a helper for a user-owned Lua state. The helper saves the stack
top, loads and executes the chunk, expects one result, and restores the
original top through an RAII guard. A load or execution error becomes a C++
exception. The result must be convertible through the Lua string-access path
used by the implementation; applications should deliberately return a string.

The D port enables its native bridge with the `DSLtkLua` version identifier
and declares the required C functions. In both languages, the caller creates,
configures, and destroys the Lua state. The bridge's stack restoration is a
local resource guarantee, not ownership of the runtime or a guarantee that
the script left all global Lua state unchanged.

## Diagnostics and source correspondence

Preprocessing can change both text length and line structure. A parser error
offset in the expanded source is not automatically an offset in the original
file. Includes and script output make the relationship more complicated.
DSLtk does not supply a full source-map representation connecting every output
span to a macro invocation or included file. A tooling application should
design that correspondence if precise original-source diagnostics matter.

For small command-line DSLs, retaining the expanded source alongside the
original may be sufficient. A diagnostic can identify that it refers to
expanded input and show the relevant excerpt. For an IDE, richer provenance
is likely necessary. The important point is to choose the user-facing
contract rather than let the loss of correspondence become an accidental
behavior discovered only after an error report is confusing.

## Keeping the preprocessing stage testable

Tests should cover quoted identifiers, nested macro arguments, recursive
definitions, inactive branches containing comments, include-depth exhaustion,
and malformed conditionals. An in-memory include callback makes these tests
independent of filesystem layout. A deterministic script callback can test
the directive path without requiring Lua, while a separate optional test can
exercise the native bridge when the dependency is available.

The reference sections below show the supported directives and both language
spellings. Use them as building blocks for a stated DSL preprocessing policy,
not as evidence of full C compatibility. The resulting language is easier to
reason about when macro syntax, include resolution, script generation, and
the later parser remain distinct stages with observable inputs and failures.
