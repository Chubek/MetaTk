## Reflection is a boundary between two vocabularies

Enum reflection is most useful when a closed C++ vocabulary meets an open
external spelling. A parser reads `identifier`, a diagnostic prints `Number`,
or a configuration file requests a mode. The enum already defines which
choices are legitimate. Reflection avoids maintaining a second hand-written
name table that can diverge from the declaration. It does not decide whether
an external user may select a particular value; that remains application
policy after the spelling has been recognized.

The header embeds the public headers of `magic_enum` version 0.9.8 and
re-exports them through `dsl`. Embedded code is still a dependency in the
source-provenance sense, even though default builds need no separate package.
The license notices and upstream version are part of the source artifact.
Do not replace this precise fact with a claim that the reflection algorithm
was invented inside DSLtk. A single-file distribution can contain several
authors' work without requiring several installed libraries.

### Why the numeric range matters

C++20 has no general standard mechanism that enumerates all declared enum
members. The embedded implementation uses compiler-supported signature
information and a configured candidate domain. For ordinary enum reflection,
the default numeric range is from minus 128 through 127. A sparse enum with
values 2, 7, and 9000 can therefore appear to have only its small members until
the customization range is widened. This is a discovery limitation, not a
change in the enum's C++ type or its underlying representation.

The cost of widening the range is compile-time work. A sparse protocol with
widely separated numeric values may force the compiler to consider many
non-enumerator candidates. A project should configure the narrowest domain
that contains its intended values, and measure build behavior for large ranges.
The value-specific `enum_name<Value>()` path is useful when a particular
enumerator is already known as a template argument. That path does not need
to discover it by scanning the ordinary configured range.

The D port demonstrates an alternative mechanism. Native enum-member
introspection exposes declarations directly; its implementation collects
members and orders values without scanning a numeric interval. The public
purpose is similar, but the performance model and discoverability limits are
different. Porting enum declarations is therefore not just changing `::` to
`.` and template brackets to exclamation marks. The selection and naming
policy should be checked on both implementations.

### Reflection does not stabilize a wire format

Suppose a protocol serializes an enum's integer value. Reordering an enum
whose members use implicit numbering changes the serialized representation,
even if reflection continues to print the same names. Conversely, serializing
names can break when a declaration is renamed. Reflection reduces repetitive
code but does not create compatibility guarantees. Persisted formats should
use explicit identifiers and a documented versioning rule.

For diagnostics, friendly names may be enough. For long-lived configuration,
the application may want aliases that remain accepted after renaming. For a
wire protocol, it may want unknown numeric values preserved rather than
rejected. Those are distinct contracts. `enum_cast` supplies a recognition
result; it does not decide whether an unknown token is fatal, ignored, or
retained for forwarding. The caller should make that decision where the open
external vocabulary crosses into the closed enum vocabulary.

### Flags are sets, not ordinary alternatives

A flags enum usually gives each independent property one bit. Combining read
and write access produces a value that may not have a single declared member
name. Ordinary `enum_name` and flags naming therefore answer different
questions. The application first declares flags intent through customization,
then uses the flags operations to inspect combinations. Zero deserves explicit
attention: it represents no selected bits, and a named zero member is not an
independent bit in the same sense as read or write.

The distinction between testing any bit and testing all requested bits is
especially important in permission-like domains. A test that asks whether
read-or-write overlaps a current value is weaker than a test that requires
both read and write. The embedded APIs expose different operations for these
roles. Code review should read the intended set relation, not merely recognize
that a function name contains the word `flags`.

### Dense enum-indexed storage

An enum-indexed array maps reflected values to compact positions. The
underlying integer need not be a safe array index: an enum value of minus one
or seven can still occupy a small dense slot. This is useful for counters,
state-specific metadata, and dispatch tables where an ordinary map would
introduce unnecessary dynamic structure. The reflection domain determines the
valid indexing vocabulary, so range configuration is part of the container's
meaning as well as the name lookup's meaning.

The application should not retain a dense index as if it were a stable external
identifier. Adding an enum member can alter the reflected ordering and the
mapping between enum values and dense slots. Store the enum or an explicitly
versioned protocol code at external boundaries. Treat the compact position as
an internal implementation detail whose purpose is convenient storage.

### Compile-time shape and runtime selection

`enum_switch` presents the selected value to a generic callback as a
compile-time constant wrapper. That can enable specialization in the callback,
but the incoming enum may still be selected at runtime. Similarly,
`enum_values` can be evaluated in a constant expression, while a loop over its
result can run at runtime. Neither operation should be described as
automatically eliminating all dispatch cost. The compiler has more information
available; whether a particular call is folded or inlined depends on the call
site and implementation.

An effective use of reflection combines these stages deliberately. Parse the
external spelling once, preserve the enum value in typed state, and dispatch
at the points where behavior genuinely differs. Repeatedly converting between
strings and enums inside a hot loop wastes the information already obtained at
the boundary. The following reference material covers the individual APIs;
the larger design principle is to make the closed vocabulary explicit early
and keep it explicit throughout the program.
