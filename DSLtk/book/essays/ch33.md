## Why explicit productions deserve a separate engine

Parser combinators express recognition as executable functions. An explicit
context-free grammar expresses it as data: nonterminals, terminals, and
productions. That representation is attractive when grammars are loaded from
configuration, generated by another tool, or inspected independently of the
host implementation. DSLtk's `CFG` turns such production data into an Earley
chart parser and constructs an AST for one accepted derivation.

The input is a vector of token strings, not raw characters. A terminal
production symbol matches an equal token string. A lexer can normalize every
numeric literal to the token `number`, but if it does so, the parser's token
leaf contains that normalized spelling rather than the original numeric text.
Applications that need both token kind and original lexeme must preserve an
external token record or choose a richer integration strategy.

The algorithm handles left recursion, epsilon productions, and ambiguous
grammars. Handling ambiguity here means recognizing through competing
derivations and retaining the first discovered one for each item identity.
It does not mean returning a packed forest of all derivations. That policy
affects downstream semantics whenever an ambiguous grammar assigns different
meanings to different parse trees.

## Grammar validation before parsing

A `CFG` has a start-symbol string and a vector of productions. Each production
has one left-hand nonterminal and one sequence of symbols. Alternatives are
represented as separate productions. Before parsing, validation rejects an
empty left-hand name, an undefined start symbol, and any right-hand
nonterminal with no defining production. Terminals need no production because
their meaning is direct token equality.

This validation catches structural omissions but does not determine whether
every nonterminal is reachable or productive. A grammar can contain a
disconnected subsystem or a cycle that never derives terminals. The chart
deduplication prevents some kinds of endless expansion during parsing, but
grammar analysis remains useful for diagnostics and performance. An application
could build a nonterminal dependency graph and use the graph utilities to
inspect such relationships.

The S-expression grammar reader uses quotedness to distinguish terminals from
nonterminals. In `(rule Expr (Expr "+" Term) (Term))`, the plus is a terminal
and the other names are nonterminals. An empty alternative `()` is epsilon.
This notation preserves a crucial distinction that a plain string list would
lose: a terminal spelled `Expr` is not the same symbol as the nonterminal
named `Expr`.

## An Earley item is a partially recognized production

An item records a production index, a dot position, an origin position, and
the AST children recognized so far. The dot separates the already recognized
prefix from the remainder. The origin remembers where this production began.
The chart position containing the item records how much input has been
consumed now. These three positions answer different questions and should not
be collapsed into one cursor.

For example, an item for `Expr -> Expr + Term` with the dot after the plus
means that the left expression and plus have been recognized, while a term
is still required. Its origin might be zero while its current chart position
is three. When that term is completed later, the item can advance and
eventually contribute an expression spanning from its origin to that later
position.

The implementation inserts an augmented start production at index zero.
Successful parsing requires a completed augmented item at the final chart
position. Returning a completed start nonterminal from some earlier position
would accept only a prefix and ignore trailing tokens. The augmented start
condition makes whole-input acceptance explicit.

## Prediction, scanning, and completion

Prediction runs when the next required symbol is a nonterminal. The parser
adds items for productions defining that nonterminal, with dot zero and
origin equal to the current chart position. A left-recursive production can
predict itself, but insertion deduplicates the same rule-dot-origin triple.
The chart reaches a closure rather than recursively calling itself forever.

Scanning runs when the next required symbol is a terminal. If it equals the
current input token, the parser advances the dot, appends a token leaf to
the recognized children, and inserts the advanced item into the next chart
position. A mismatch does not advance input. Other items at the same position
can still predict or scan different alternatives.

Completion runs when an item's dot reaches the end of its production. The
parser builds an AST node tagged with the production's left-hand name and
looks back at the chart at the item's origin. Any waiting item whose next
symbol is that nonterminal can advance, appending the completed subtree.
This is how recognition of a local phrase propagates to the surrounding
productions that requested it.

## Nullable productions require same-position closure

An epsilon production completes without consuming a token. Its completion
can advance a waiting parent at the same chart position, and that parent
may itself become complete. The implementation's loops re-read growing chart
sizes so newly inserted items at a position are processed. It also includes
a nullable fix-up for completed same-origin items already present when a
new waiting item appears.

This ordering detail is easy to miss in a simplified Earley description.
Without adequate same-position closure, a grammar's acceptance can depend on
the incidental order in which nullable items were discovered. The chart must
account for both situations: a completion appearing after its waiter and a
waiter appearing after an already available nullable completion.

The AST of an epsilon production is an inner node with no children. It is
not a missing optional tree and not an empty-value leaf. That distinction is
useful to later visitors: the grammar has recognized a real production even
though that production consumed no terminals. Semantic code may choose to
erase such wrapper nodes in a normalization pass, but the parser's result
faithfully records the chosen derivation structure.

## First-discovered derivations and their consequences

Item identity includes the rule, dot, and origin, but not the accumulated
children. When two derivations reach the same item configuration, the later
one is discarded. This bounds redundant work and provides one AST, but it
also makes derivation selection dependent on discovery order. Changing
production order can change an ambiguous grammar's returned tree.

For arithmetic, ambiguity should normally be removed through grammar design.
Separate expression, term, and factor nonterminals encode precedence more
reliably than hoping the parser's first discovery matches a desired policy.
If an application genuinely needs all parses, the current representation is
insufficient: it would need a shared parse forest or another structure that
retains packed alternatives instead of one child vector.

The distinction between acceptance and chosen meaning is important even for
non-arithmetic DSLs. An ambiguous command grammar can accept the same token
sequence under two productions with different effects. The parser will return
one tree, but that does not make the language specification unambiguous.
Testing should therefore inspect tree shape on representative ambiguous-looking
inputs, not only assert that `ok()` returns true.

## AST construction and diagnostics

Completed nonterminals become inner nodes tagged by the left-hand name.
Scanned terminals become leaves tagged `token` with the token spelling as
their value. The augmented start wrapper is not exposed as the user's root;
the successful result contains the completed start nonterminal's tree.
This regular shape makes visitor-based semantic passes straightforward.

On failure, the result reports the furthest chart position that contains
items and a deduplicated set of terminals those items are waiting for. The
position counts tokens, unlike the byte offsets used by character parser
combinators. A diagnostic formatter must translate through the original
token records if it wants a source byte location or line and column.

The expected set describes the chart frontier, not a guaranteed minimal
human explanation. A broad grammar can produce several plausible terminals
at the failure point. A language-facing formatter may group or rename them
while preserving the underlying data for tooling. Keeping parse facts and
presentation policy separate avoids embedding user-interface choices in the
recognition algorithm.

## Complexity claims need implementation context

Earley's classical bounds describe the algorithmic family under particular
data-structure assumptions. This compact implementation stores chart sets in
vectors and checks for duplicates by scanning them. It also carries and copies
AST child vectors in items. Those choices add costs beyond a textbook count
of unique item transitions. It would be inaccurate to promise the strongest
classical complexity bound for every operation in this particular code.

For moderate DSL grammars, clarity may be more valuable than elaborate
indexes. For large inputs, measure chart sizes, duplicate-check work, and tree
copying. Potential improvements include indexing items by identity,
indexing waiting items by nonterminal, and separating recognition from packed
tree construction. Those are meaningful extensions because the current
implementation exposes where the work occurs.

## A small grammar that demonstrates left recursion

```cpp
#include "DSLtk.hpp"
#include <cassert>
#include <iostream>
int main() {
  auto grammar = dsl::sexpr_grammar(R"(
    (grammar (start Expr)
      (rule Expr (Expr "+" Term) (Term))
      (rule Term ("number")))
  )");
  auto result = grammar.parse({"number", "+", "number"});
  assert(result.ok() && result.position == 3);
  auto failure = grammar.parse({"number", "+"});
  assert(!failure.ok() && failure.position == 2);
  std::cout << result.tree->dump() << '\n';
}
```

The left recursion is explicit rather than transformed away. The failure
case checks that the parser reaches the end of the incomplete sequence and
still requires a term. The reference sections below show programmatic and
typed-production construction as well as the S-expression form. All three
ways lead to the same runtime production representation and the same chart
algorithm.
