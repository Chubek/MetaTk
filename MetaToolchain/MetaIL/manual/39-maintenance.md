# 39. Extending and maintaining MetaIL

Use `lua/metail/ir.lua` as the canonical structure. The parser, native C bridge,
C++ DSLtk mapping, emitter, analyses, and transforms must agree. Adding an operator
requires updating its arity and semantics consistently, not just teaching one
frontend to accept a new spelling.

The main extension points are:

| Concern | Location |
|---|---|
| Parsing and canonical IR | `lua/metail/parser.lua`, `ir.lua` |
| Analysis algorithms | `lua/metail/analysis.lua` |
| Procedural transforms | `lua/metail/transform.lua` |
| DSL registration and guards | `lua/lkopt.lua`, `lua/metail/guards.lua` |
| C structured conversion | `MetaIL.c`, `MetaIL.h` |
| Native C++ builders | `MetaIL.hpp` |
| Kernel metadata/search | `lua/metail/catalog.lua`, `KernelRegistry.hpp` |

Bundled additions are generated by `tools/generate_kernels.py`. Preserve the
original `ConstantFolding.optk`, the 200 base additions, and the 120 numeric
additions. Run the generator with `--check` to verify exact content and inventory.
Custom local kernels should live in a separate directory loaded explicitly.

Any rewrite that discards, duplicates, or reorders operands needs the appropriate
purity reasoning, including traps. Add a regression case that would fail if the
guard were removed. Analysis extensions must compute real results; named no-op
registrations are not implementations.

Keep owning C++ objects outside Lua API calls that can longjmp. The C bridge's
protected boundaries and tracked allocation cleanup are part of its correctness
contract, not incidental implementation detail.
